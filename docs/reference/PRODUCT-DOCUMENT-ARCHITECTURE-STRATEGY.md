# Product Document Architecture Strategy

> 상태: 설계 제안. 현재 실행 정책이나 설치 템플릿을 대체하지 않는다.
> 작성일: 2026-09-09
> 범위: Product 문서 지도, 작성 책임, 현행화, 점진 이행. Audit/PoC 규칙은 유지한다.

## 1. 결정 요약

Product를 6개 파일 안에서 운영하는 제한을 풀고, 제품 개발에 필요한 정보별로 원본 위치를 정한다. 문서 종류를 줄이는 대신 중복 서술, 날짜순 Delta 누적, 실행 기록과 현재 계약의 혼합을 줄인다.

- 기본 구분은 제품/요구사항, 설계, 개발, 검증, 배포/운영, 결정, 사용자 안내다. 아래 12개 문서 영역은 정보의 자리이며 모든 파일을 init에서 빈칸으로 생성하라는 뜻이 아니다.
- 파일 분할 단위는 독립적으로 변경하고 검토할 기능/도메인/서비스다. 모든 REQ/API/테스트 ID마다 파일 하나를 강제하지 않는다.
- 현재 명세는 해당 위치에서 현행화하고 변경 이유는 CR/ADR에 연결한다. 실제 실행 결과는 실행별 증적으로 보존한다.
- 기존 ID, 승인, 미완료 의무, Git 기준과 링크를 유지한다. 문서 재배치 자체는 계약 변경 승인이나 Gate 통과가 아니다.
- 이번 작업은 설계와 원본 밖 파일럿까지다. 실행 정책, 사용자 프로젝트 원본, CLI, Dashboard, 필수 산출물 목록을 즉시 바꾸지 않는다.

작성 항목의 기준은 [문서별 작성 계약](PRODUCT-DOCUMENT-WRITING-CONTRACTS.md), 현재 실행 중인 조회/증적 정책은 [Current Context And Evidence](../core/CURRENT_CONTEXT_AND_EVIDENCE.md)다.

## 2. 문제와 근거

장기 Product 프로젝트의 읽기 전용 관찰에서 계약 원장 약 1,182줄, 검증/릴리즈 원장 약 939줄과 여러 날짜별 변경 절을 확인했다. 줄 수는 관찰 당시 값이며 토큰 사용량이나 비용을 뜻하지 않는다.

주된 문제는 다음과 같다.

1. 현재 요구/계약을 확인하기 위해 기준 본문, 여러 Delta, 승인 문구를 조합해야 한다.
2. 요구/설계/추적/결과 원장에 같은 설명이 재작성돼 변경 시 여러 원본처럼 동작한다.
3. 문서 상단의 Approved와 일부 새 절의 candidate, 과거 Pass와 현재 Pending이 섞인다.
4. 테스트 정의, 부분 실행, 재시험, 릴리즈 판단이 한 결과 문서에 누적된다.
5. 6개 파일명에 의존하는 검사/화면 때문에 단순 파일 분할도 호환 작업이 필요하다.

공개 저장소에는 실제 프로젝트 본문, 고객/운영 정보, 비공개 자료, 세션 식별자를 넣지 않는다. 파일럿 원문/해시/상세 비교는 로컬에만 보존하고 공개 회귀에는 합성 자료를 쓴다.

## 3. 문서 지도

기존 `docs/artifacts/`의 분류를 재사용한다. 아래는 목표 배치 예시이며 기존 파일을 이 이름으로 일괄 변경하지 않는다. 꺾쇠 부분은 실제 기능/서비스 이름으로 대체한다.

```text
docs/
  product/
    README.md                         # 문서 지도, 현재 범위/미해결 항목의 링크
    PRODUCT_BRIEF.md                   # 제품 목적/사용자/범위 개요
    ADR_LOG.md                        # 결정 색인; 결정 전문은 건별 분리 가능
    PRODUCT_TRACEABILITY.md           # 관계 원장/파생 뷰의 전환 경로
  artifacts/
    01-requirements/
      README.md                      # 요구사항 목록과 상세 위치
      <feature>.md                   # 기능별 요구/인수조건
    02-design/
      architecture/                  # 전체 구조, 실행/배포 뷰
      function/                      # 복잡한 기능 흐름/상태 전이
      program/                       # 공개 모듈/타입/인터페이스 계약
      screen/                        # 여정/화면 상태/디자인/시안 연결
      api/                           # API와 연동별 계약, 스키마 연결
      data/                          # 용어/ERD/스키마/이관
      security/                      # 신뢰 경계/권한/위협/보호 기준
      development-standard/          # 환경/코딩/테스트/빌드 기준
      integration/                   # 여러 서비스에 걸친 설계
    03-test/
      <feature>.md                   # 테스트 정의와 선행조건
    04-review/
      <verification-batch>/           # 실행 결과, 해당 소스 기준, 증적
    05-change/                       # 변경 제안/승인/영향/미해결 결정
    07-release/
      <release>/                     # 릴리즈 범위/판정/알려진 문제
  operations/                        # 배포/롤백/모니터링/복구 절차
  user-guide/                        # 사용자 시작/사용/설정/문제 해결
  backlog/                           # 우선순위/진행/다음 행동의 기존 원장
  reviews/                           # 검토 의견; 현재 명세를 대신하지 않음
  runs/                              # 필요한 위임/실행 기록; 선택 정책 유지
```

`PRODUCT_ARCHITECTURE.md`, `PRODUCT_CONTRACTS.md`, `REGRESSION_AND_RELEASE_REPORT.md`를 포함한 기존 6종 경로는 이행 기간 유지한다. 후속 CLI 구현의 상세 지원 범위는 [내용 검사·추적·통계 호환](../core/CURRENT_CONTEXT_AND_EVIDENCE.md#32-product-내용-검사추적통계-호환)을 따른다. 일부 검사 호환만으로 전체 작성/승인/릴리즈 경로가 준비됐다고 보지 않으며, 기존 프로젝트 원장의 재배치는 7절 C의 확인과 승인을 거친다.

디렉터리는 정보 위치이고 Gate는 작성/승인 시점이다. 승인된 변경으로 Gate 1에 재진입해도 이전 설계/구현/검증 파일을 지우지 않는다. 현재 적용 범위와 과거 릴리즈의 승인 범위를 구분해야 한다.

## 4. 정보 원본과 관계

| 정보 | 원본 | 다른 문서의 역할 |
| --- | --- | --- |
| 제품 목표/이번 범위 | 제품 개요와 승인된 범위 결정 | 기능 문서에서 링크 |
| 요구 동작/AC | 기능별 요구사항 | 설계/테스트에서 ID와 위치 참조 |
| 시스템 공통 정책 | 해당 아키텍처/보안/데이터/개발 기준 | 적용 범위와 예외만 기능에 기록 |
| API/데이터/UI/프로그램 상세 | 해당 설계 문서 또는 명시한 스키마 원본 | 요약/색인은 ID, 제목, 위치만 |
| 테스트 입력/기대값 | 테스트 정의 | 구현된 테스트 코드와 연결; 실행 결과에는 반복하지 않음 |
| 실제 관측/성공/실패 | 실행별 결과와 로그 | 현황 표는 해당 결과 링크로 파생 |
| 미해결 검증/결함의 현재 의무 | 기존 FIND/ISSUE/CR 중 해당 항목의 관리 원본 한 곳 | 추적/릴리즈/백로그는 링크만; 과거 시험 결과를 수정하지 않음 |
| 승인/변경 이유 | 기존 승인 기록, CR/ADR | current 표식으로 승인을 대체하지 않음 |
| 현재 구현 상태 | 관련 변경과 검증을 확인한 추적 기록 | 파일 존재/PR 병합만으로 Verified 추론 금지 |

관계도 하나의 소유 위치를 정한다. 요구사항은 AC를 소유하고, 설계는 구현할 요구 ID를 참조하며, 테스트는 검증할 요구/계약 ID를 참조한다. 실행 기록은 테스트 ID와 대상 소스에 연결한다. 역방향 연결은 이 관계들에서 파생한다.

기존 수동 추적표를 즉시 없애지 않는다. 파생 인덱스가 도입되면 검토자가 판단한 상태/이슈/승인 근거는 보존하고, ID 관계와 경로만 재생성 가능한 정보로 구분한다. Markdown 표와 별도 YAML에 같은 본문/관계를 두 번 작성시키지 않는다. 단순 ID 언급은 관계 선언이나 소유권 증명이 아니다.

OpenAPI, DB migration, 테스트 코드/리포트가 있으면 파일을 연결한다. 생성 스키마는 실제 구현 모습의 근거이며 승인된 동작과 동일하다는 증명은 아니다. 의도와 구현이 다르면 drift로 드러내고 명세를 코드에 맞춰 자동 덮어쓰지 않는다.

## 5. 작성과 성장 규칙

### 5.1 기본 작성

문서마다 목적/범위, 작성 책임 역할, 적용 상태/범위, 원본 연결을 짧게 표시한다. 기존 metadata가 있으면 재사용하고 새 필수 중복 필드를 만들지 않는다. 상세 작성 항목은 [작성 계약](PRODUCT-DOCUMENT-WRITING-CONTRACTS.md)을 따른다.

- 결정에 필요한 조건/입출력/예외/근거를 쓴다. 작업했다는 서술이나 공통 절차 전문을 계약에 붙이지 않는다.
- 좁은 표는 목록/비교용, 조건이 많은 동작은 짧은 번호 목록이나 하위 절로 쓴다. 긴 문장을 한 표 셀에 밀어 넣지 않는다.
- 분량 목표나 페이지 수로 계약을 생략하지 않는다. 한 조건이 여러 문서에 필요하면 원본과 적용 범위를 연결한다.
- 미확정이면 이유와 결정할 시점을 남긴다. 이미 해결된 TBD/질문은 현재 문서에서 현행화하고 결정 근거를 연결한다.
- 개요/색인은 긴 요약을 별도로 쓰지 않는다. 제목/ID/원본 링크와 필요한 현재 범위 안내면 충분하다.

### 5.2 분할/병합 기준

다음 중 하나가 실제로 발생하면 독립 상세 문서로 분리한다: 서로 다른 기능을 매번 함께 읽음, 서로 다른 담당자의 수정 충돌, 별도 계약/검토 주기, 조건/예외가 목록의 한 행으로 설명되지 않음.

반대로 늘 함께 바뀌며 독립 의미가 없는 짧은 문서는 합쳐도 된다. ID 수, 페이지 수, 파일 수에 고정 임계값을 두지 않는다. 문서 분할 때문에 새 업무 ID를 만들거나 기존 ID를 재번호하지 않는다.

### 5.3 현행화와 이력

1. 변경 제안은 관련 CR/검토 기록에서 현재 명세와 구분한다.
2. 승인 범위가 확인되면 해당 현재 계약을 수정한다. 재배치와 의미 변경은 diff/PR에서 구분한다.
3. 이전 결정/계약은 기존 Git/CR/ADR 또는 필요한 보존 파일에 연결한다. 폐기된 내용에는 대체 위치/적용 범위를 남긴다.
4. 기존 테스트 실행 결과는 수정해서 최신 Pass로 만들지 않는다. 새 실행 기록을 만들고 현재 요약이 그 결과를 가리키게 한다.
5. 미완료 시험/결함은 릴리즈 범위가 바뀌어도 완료로 바꾸지 않는다. 계속 적용되는 의무와 후속 제공 전 의무를 구분한다.

미완료 의무의 관리 위치는 총괄이 기존 FIND/ISSUE/CR 중 하나로 정한다. 별도 새 원장을 만들지 않고 적용 조건/대상 릴리즈 또는 기능, 담당 역할, 관련 결과/시험, 종료 판단 근거를 그 항목에 둔다. 현재 릴리즈에서 제외해도 후속 제공 전 필수 의무는 삭제하지 않는다. 검증 담당이 재시험 근거를 제시하고 총괄이 기존 승인 기준에 따라 종료 여부를 확인한다.

문서 전체의 최신 날짜/Approved 값으로 하위 초안을 승인하지 않는다. 같은 ID의 현재 기준이 충돌하면 총괄이 결정 근거를 확인한다. 현재 명세 분할 시 승인된 과거 버전에서 여전히 유효한 조건도 함께 추적한다.

## 6. Gate와 역할

| 단계 | 판단할 정보 | 책임 중심 |
| --- | --- | --- |
| Phase 0 | 목표/사용자/범위 후보/위험 | 총괄 + 제품/요구 담당 |
| Gate 1 | 이번 요구/인수조건/제외 범위 | 요구 담당, 총괄의 승인 확인 |
| Gate 2 | 적용 설계/UX/UI/API/DB/보안/개발/배포 가정 | 설계/경험설계 담당 |
| Gate 3 | AC별 검증 방법/입력/기대값/환경 | 품질 담당 |
| Impl | 승인 범위 구현/영향 시험/실제와 다른 명세 후보 | 개발 담당; 총괄이 공통 상태 관리 |
| Gate 4 | 확정 대상의 실행 결과/미해결 위험 | 품질 담당, 필요 시 새 문맥 리뷰 |
| Gate 5 | 릴리즈 범위/증거/운영·사용 안내의 준비 | 총괄이 승인 확인 |

모든 역할 작업창이 동일 문서를 복제해 소유하지 않는다. 한 기능의 담당자는 해당 원본을 갱신하고 총괄은 색인/추적/승인을 확인한다. 개발환경 병렬 준비나 사용자 역할 배정 정책을 이번 문서 구조로 새로 변경하지 않는다.

문서 유형은 공유할 수 있지만 이 제안의 첫 적용 대상은 Product다. Product도 요구/보안/검증을 유지하며 Audit은 상세 추적/공식 승인/증적/제출 요건을 추가한다. Audit 검사 완화나 PoC 세트 통합은 별도 작업이다.

## 7. 호환성 이행 계획

### A. 설계와 로컬 파일럿 (이번 범위)

- 이 문서와 작성 계약을 검토한다.
- 진행 중인 프로젝트의 기능 하나를 저장소 밖 스냅샷으로 분리한다. 원본/정책/승인/서비스는 변경하지 않는다.
- 조건 보존, 후보/현재 구분, 관계/링크, 읽기 범위, 수정 위치를 확인한다. 토큰/비용 절감이나 제품 QA 통과로 보고하지 않는다.

### B. 조회/검사의 이중 형식 지원 (점진 구현)

2026-09-10 후속 구현에서는 절 조회에 이어 Product 내용/Gate 검사, 추적 행/요구·회귀 통계와 seed 확장에 명시적 상세 링크 지원을 추가했다. 합성 legacy/split/mixed 회귀로 검증했으며 실제 프로젝트 원본은 이동하지 않았다. 아래 표의 설치/작성 경로, 승인 이력 비교, 릴리즈 및 Dashboard 전체 호환은 아직 후속 범위다.

| 현재 결합 지점 | 확인한 소스 | 필요한 변경/회귀 |
| --- | --- | --- |
| 설치/필수 경로 | `vulcan.py`: `PRODUCT_ARTIFACT_TEMPLATES`, `PRODUCT_REQUIRED_ARTIFACTS_BY_GATE`, `install_product_artifacts` | 기존 6종 기본 유지, 명시적 새 배치 지원; upgrade 원본 보존 |
| 내용/Gate 검사 | `collect_product_profile_findings`, `validate_product_trace`, `product_verification_result_findings` | 파일 수 대신 요구/계약/검증 내용 확인; 링크만 있는 빈 색인으로 통과 금지 |
| 추적/통계/Run 입력 | `parse_product_trace_rows`, `compute_product_stats`, `build_trace_graph`, `build_product_worker_preset` | 원본/참조 구분, 여러 문서의 동일 ID 중복 집계 방지, Run 선택 유지 |
| 절 조회 | `vulcan_core/document_context.py`: `lookup_sections` | 조회 호환 MVP: 요구/시험 폴더, 명시적/제한된 참조 조회, 공통 조건 미수집 표시; 의미상 완전성/승인 판정은 별도 |
| 승인/소스 비교 | `product_gate_approval_snapshot`, `product_run_matches_approval` | 문서 경로 이동과 내용/승인 범위 변화 구분, 과거 승인 전체 승격 금지 |
| 릴리즈 | `vulcan_core/release.py` | 현재 결과/미완료 의무/릴리즈 승인 연결; 모든 과거 실행을 새 필수검사로 반복하지 않음 |
| Dashboard | `dashboard/src/app/projects/[id]/page.tsx`, `DocList.tsx`, `CurrentGatePanel.tsx` | `Product docs 6/6`을 그대로 새 완성도로 쓰지 않음; 종류별 원본/현재 범위/이력 탐색 |
| 회귀/지침 | `run_fixture_smoke.py`, Product 관련 unit, Core/Codex/Gemini/사용자 안내 | legacy/split/mixed fixture의 같은 의미 검사; 설치 동작과 안내 동시 반영 |

새 DB, 별도 필수 registry, 새 CLI 명령은 선결 조건이 아니다. 기존 문서 metadata/표/명시적 링크에서 파생 가능한 조회 모델을 먼저 검토한다. 참조 조회는 프로젝트 내 허용 경로만 사용하고 깊이/양 제한, 순환, 누락, 잘림, 충돌을 보고해야 한다.

설계 파일럿 당시 기본 탐색은 `docs/product`와 `docs/artifacts/02-design`뿐이었다. 후속 조회 호환 MVP는 요구사항/시험 경로와 제한된 명시적 참조 조회를 추가한다. [현재 조회 범위/제한](../core/CURRENT_CONTEXT_AND_EVIDENCE.md#31-분리-문서-조회-호환-mvp)을 기준으로 확인한다. 공통 조건 제목에 특정 키워드를 붙여 우연히 읽히게 하는 방법을 새 문서 작성 규칙으로 삼지 않는다.

### C. 실제 기능 하나를 승인 후 이동

- 지원 도구/템플릿/Core/adapter 지침이 읽기와 쓰기 모두 새 원본 위치를 인식하는지 확인한다. 기존 6종에 상세를 다시 덧붙이는 구형 작성 경로가 남으면 이동을 보류한다. 이미 열린 담당 작업에도 변경된 작성 위치를 전달한다.
- 이동 전 ID/조건/승인/링크와 작업트리 상태를 저장한다. 자동 추출 후 사람이 의미 차이를 확인한다.
- 기존 상세 원본을 새 위치로 옮기고 원래 절에는 연결/호환 앵커를 남긴다. 양쪽에 편집 가능한 같은 계약을 두지 않는다.
- 조회, trace/status/통계, Run 입력, QA/릴리즈, Dashboard를 old/new/mixed에서 비교한다. 이전 버전의 실패는 보존하고 현재 범위 검사와 구분한다.
- 경로 이동으로 승인된 내용이 바뀐 것으로 보이거나 누락/중복이 생기면 멈춘다. 소유자가 선택한 변경만 되돌릴 수 있게 migration diff를 별도로 둔다.
- 효과가 확인되면 변경하는 기능부터 순차 적용한다. 이전 6종 호환 경로의 제거는 모든 소비자와 기존 링크 지원이 검증된 후 별도 결정한다.

## 8. 검증 기준

| 질문 | 통과 기준 |
| --- | --- |
| 기능의 현재 요구/제약을 찾는가? | 목록에서 원본으로 이동 가능; 조건/공통 제약 누락과 미분류를 숨기지 않음 |
| 변경 시 어느 파일을 수정하는가? | 계약 원본 한 곳과 필요한 결정/테스트/추적 영향이 식별됨; 같은 본문을 여러 곳에 복사하지 않음 |
| 요구가 사라지지 않았는가? | 기존 ID/AC와 예외/권한/미완료 의무가 대응; 누락은 명시 |
| 현재/과거/후보를 오판하지 않는가? | 후보를 승인/Implemented/Pass로 올리지 않음; 과거 Pass만으로 현재 합격 선언 금지 |
| 검사와 화면이 같은 뜻을 읽는가? | legacy/split/mixed 결과 일치, 중복 소유/깨진 링크/빈 색인 negative test |
| 실제 부담이 줄었는가? | 읽은 원문/선택 구간 크기, 문서 왕복, 보정량을 각각 보고; 파일 수 증가도 함께 표시 |

전체 원장 읽기와만 비교하면 기존 절 조회 효과를 문서 분할 효과로 오인할 수 있다. 같은 기능에 대한 기존 절 조회/수동 선택과 새 분할 문서의 비교도 필요하다. 로컬 파일럿만으로 모델 비용/품질 우위를 주장하지 않는다.

파일럿 결과: [Product Document Architecture Pilot](PRODUCT-DOCUMENT-ARCHITECTURE-PILOT.md).

- Atlassian은 간결한 PRD에 목표/가정/사용자 스토리/제외 범위를 두고 상세 스토리와 화면 설계를 연결한다. [PRD 작성 방식](https://www.atlassian.com/agile/product-management/requirements)

- arc42는 구조/실행/배포/공통 개념/결정/품질/위험/용어의 정보 자리를 제공한다. 문서 파일 12개 강제가 아니다. [Template Overview](https://arc42.org/overview/)
- Google SRE는 모니터링/장애 대응/용량/변경/성능 등 서비스별 운영 준비를 다룬다. [Production Readiness](https://sre.google/sre-book/evolving-sre-engagement-model/)
- 사용자 안내의 튜토리얼/절차/참조/설명 구분은 Diataxis를 참고한다. 전체 개발 프로세스를 대체하지 않는다. [Diataxis](https://diataxis.fr/)
