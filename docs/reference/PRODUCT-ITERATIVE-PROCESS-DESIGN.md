# Product Iterative Process Design

- 상태: Product 운영 설계안 / 단계 1 상태 계약 프로토타입 구현, 운영 runtime 미연결
- 작성일: 2026-09-11
- 검토 기준: `aacbf7c` main과 PR #32의 업무 분석 파일럿
- 범위: Product만. Audit/PoC의 단계·검사·문서 정책은 이번에 변경하거나 재설계하지 않는다.
- 연계: [업무 분석 가이드](PRODUCT-DISCOVERY-AND-VALIDATION-GUIDE.md), [운영 시나리오](PRODUCT-ITERATIVE-PROCESS-SCENARIOS.md)

이 문서는 앞으로 구현할 동작을 정의한다. 현재 프로젝트에서는 [기존 Product 운영 기준](../core/PRODUCT_PROFILE_BASELINE.md)이 계속 유효하다. 아래 단계 이름이나 상태값을 `session.json`에 수동으로 넣거나 기존 Gate 검사를 우회하지 않는다.

단계 1의 구체적 직렬화·내부 API·조회/쓰기 차단·신뢰 경계는 [상태 계약 구현 범위](PRODUCT-PROCESS-CONTRACTS.md)에 정리했다. 설계 자료 전체를 프로젝트 에이전트의 필수 읽기 목록에 추가하지 않는다.

## 1. 결정과 목적

Product를 **기획·설계, 구현, 인수 검증**의 세 구간으로 운영한다. Phase 0/요구/상세 설계/시험 계획 사이의 별도 전환과 형식적인 완료 승인은 없앤다. 배포·릴리즈는 인수 이후 필요할 때 수행하는 별도 승인 행동이지 매 기능의 네 번째 구간이 아니다.

문서의 역할과 품질 기준은 합치지 않는다. 문제·업무·요구·설계·시험 정의·실행 결과는 각 원본에서 연결한다. 성공 기준은 단계 수나 속도 자체가 아니라 사용자 의도에 맞는 제품을 만들고, 기능이 늘어도 현재 계약과 검증 근거를 찾을 수 있는가다.

운영 단위는 **이번에 합의한 변경 묶음**이다. 기존 작업/이슈/PR의 범위와 SCN/REQ/계약을 사용하며 새 ITER-ID, Run, Wave, 중복 업무 원장을 필수화하지 않는다. 제품 전체나 모든 미래 기능을 한 번에 승인·완료시키지 않는다.

## 2. 세 구간의 작업과 경계

| 구간 | 실제 작업 | 끝에서 확인할 것 |
| --- | --- | --- |
| 기획·설계 | 문제/사용자/경계, 흐름·규칙·예시, REQ/AC, UI/API/DB/보안·운영 설계, 시험 방법을 필요한 만큼 왕복 | 구현 범위와 관련 계약, 중요한 미정 사항, 관측 가능한 인수조건과 검증 방법이 명확한가 |
| 구현 | 승인 범위의 코드·설정·담당 테스트 작성, 통합, 영향 문서 현행화 | 구현과 통합 소스, 실제 self-check 결과, 남은 결함/환경 차단을 인계할 수 있는가 |
| 인수 검증 | 통합된 소스로 업무 시나리오·회귀·보안/품질 조건 검증, 실제 결과와 미완료 의무 정리 | 필수 검증이 충족됐고 권한 있는 인수 책임자가 해당 결과를 수용했는가 |

기획·설계 안에서는 사용자의 한 답이 API/데이터 검토로 이어지고 다시 업무 질문으로 돌아와도 같은 구간이다. 모든 제품 문서를 완성해야 구현할 수 있는 것은 아니다. 다만 선택한 구현 범위의 핵심 동작·권한·데이터 의미·검증 기준을 TBD로 둔 채 착수하지 않는다. 관련 없는 미래 기능과 영향 없는 미정 사항은 분리한다.

환경 조사나 기술 검토와 실제 제품 구현을 구분한다. 기획·설계 중 독립 실험이 필요하면 실험 범위와 격리 위치를 합의하고 결과를 후보로 반환한다. 일반적인 기획 허가를 제품 코드 작성 허가로 확대하지 않는다.

## 3. 사용자 결정과 자율 진행

| 상황 | 총괄 에이전트의 행동 | 사용자 확인 |
| --- | --- | --- |
| 이미 확인된 자료 정리, 설계 대안, 시험 계획 | 관련 원본만 읽고 현재 구간에서 진행 | 매 문서마다 재승인하지 않음 |
| 업무 규칙·권한·범위가 미정이거나 기존 합의와 충돌 | 대안/영향과 구체적 예시를 질문. 영향받는 확정만 보류 | 업무 결정자에게 확인 |
| 기획·설계에서 구현으로 진입 | 범위·계약 기준·검증 계획과 남은 위험을 연결 | 해당 범위의 명시적 구현 허가 또는 이미 유효한 구체적 위임 근거 필요 |
| 구현 완료 후 검증 실행 | 실제 대상 소스와 환경을 확인하고 승인 범위의 시험 수행 | 검증 실행이 이미 허용됐다면 별도 구간 이동 승인 불필요 |
| 인수 중 승인 계약을 만족시키지 못하는 코드 발견 | 결함/증적을 기록하고 구현 담당에게 수정 범위 전달 | 해당 종류의 수정이 위임 범위 안이면 자율 수정·재시험. 아니면 수정 허가 요청 |
| 요구 의미, 보안 경계, 외부 영향·비가역 데이터 작업 변경 | 기획·설계의 영향 부분으로 반환하고 변경 후보 제시 | 기존 변경/보안 승인 유지 |
| 검증 충족 후 결과 수용 | 실제 결과·대상·잔여 위험을 인수 후보로 보고 | 사용자 또는 사용자가 지정한 권한 있는 인수 책임자의 수용 근거 필요 |
| merge, 운영 배포, 공개 릴리즈, 데이터 이관 | 각각의 대상/영향과 허가를 확인 | 인수나 구현 허가를 이 행동의 허가로 확대하지 않음 |

"알아서 진행"은 합의한 목표·범위·금지 사항 안의 위임으로 해석한다. 그 범위가 불명확하면 필요한 부분만 확인한다. 테스트 통과, reviewer 동의, 에이전트 자신의 완료 보고는 사용자 수용 근거가 아니다. 사람의 문구를 프로그램이 의미 해석해 자동 승인하지 않는다.

승인 근거는 기존 작업/결정/PR에 연결하고 대상 범위, 원본의 당시 내용 기준, 허용한 행동을 식별한다. `--approved` 같은 플래그를 넣었다는 사실만으로 실제 사용자 동의를 증명하지 않는다. 범위가 달라지면 이전 허가를 새 기능에 재사용하지 않으며, 내용 변화 없는 정리 때문에 전체 업무 합의를 반복하지 않는다.

## 4. 반복과 상태 의미

다음은 목표 동작이며 현재 CLI 명령 예시가 아니다.

| 시작 | 사건 | 다음 상태와 범위 |
| --- | --- | --- |
| 기획·설계 | 중요한 질문이 남음 | 같은 구간. 영향 작업 보류, 독립적으로 허용된 조사는 계속 |
| 기획·설계 | 준비 기준 충족 + 해당 범위 구현 허가 | 구현 |
| 구현 | 인계할 소스·self-check가 준비됨 | 인수 검증. 아직 모든 인수 시험이 실행됐다는 뜻은 아님 |
| 인수 검증 | 제품 결함, 수정 범위/허가 명확 | 구현 → 영향 재검증. 요구/전체 기획을 다시 만들지 않음 |
| 구현/인수 검증 | 기대 동작이 불명확하거나 계약 변경 필요 | 기획·설계의 영향 부분. 기존 결과는 이력으로 보존 |
| 인수 검증 | 환경 차단 또는 증적 누락 | 같은 구간에서 보류 사유 기록. Pass나 기능 제외로 바꾸지 않음 |
| 인수 검증 | 필수 결과 충족 + 수용 근거 | 이번 변경 완료. 제품 개발의 영구 종료는 아님 |
| 이번 변경 완료 | 새로운 기능/업무 변경 | 새 범위의 기획·설계. 기존 ID/계약/결과는 재사용하거나 영향 부분만 갱신 |
| 이번 변경 완료 | 계약이 명확한 국소 결함 수정 | 해당 수정 허가와 기준이 있으면 구현부터. 없으면 범위 확인 |

이전 완료 목록을 지워 새 반복을 표현하거나 과거 Pass를 새로운 코드에 옮겨 붙이지 않는다. 미완료 의무는 당시 실행 기록과 관리 원본에 남으며 새 반복을 시작해도 사라지지 않는다. 현재 작업의 완료와 전체 릴리즈 가능 여부는 별도로 판단한다.

총괄은 한 개의 현재 실행 묶음/통합 상태를 관리한다. 다음 기능의 독립적인 기획 후보나 검토는 병렬로 할 수 있지만 현재 승인된 원본을 몰래 교체하거나 해당 구현 허가까지 얻은 것으로 보지 않는다. 다중 active Wave나 자동 스케줄러는 추가하지 않는다.

## 5. 문서·역할·검증

| 원본/책임 | 갱신 기준 |
| --- | --- |
| Brief / 총괄·업무 | 목표·범위·사용자·시나리오 지도와 상세 링크. 매 반복의 대화 전문을 누적하지 않음 |
| 업무·요구 상세 / 업무·요구 담당 | 맥락·액터·흐름·규칙·REQ/AC. 현재 내용, 후보, 미정/결정 근거 구분 |
| Architecture/Contracts와 설계 상세 / 설계·경험설계 | 합의한 동작의 UI/API/DB/보안·운영·개발 기준. 기술 결정은 필요한 ADR에 연결 |
| 시험 계획 / 품질 | 설계 시 입력·행동·기대값과 실행 방법 작성. Planned를 Pass로 변경하지 않음 |
| 코드와 담당 테스트 / 구현 | 허용된 범위 구현과 self-check. 공통 문서 변경은 소유자에게 후보 전달 |
| 실행 결과 / 품질 | 실제 소스·시험 기준, 명령/관측/증적, 실패·환경 차단·미실행 기록. 재시험은 새 실행 묶음 |
| Traceability/현재 결과·수용 근거 / 총괄 | 원본 간 연결과 현재 대상 판단. 과거 실행은 보존하되 현재 통과 근거와 혼합하지 않음 |

현재 6종 진입점과 [기능별 원본 작성](../core/PRODUCT_DOCUMENT_WRITING.md)을 유지한다. 단계 축소와 파일 이동은 별개다. 업무 상세 템플릿·소유 경로는 [업무 분석 가이드](PRODUCT-DISCOVERY-AND-VALIDATION-GUIDE.md)에 따라 후속으로 정하고, 미지원 경로를 검사에서 읽는다고 주장하지 않는다.

역할별 작업창은 [협업 계약](../core/COLLABORATION_PROTOCOL.md)에 따라 사용한다. 사용자와의 결정 창구와 공통 상태 작성자는 총괄 한 곳이며 담당자들은 실제 배정 범위만 수행한다. Product의 Run/Wave·외부 CLI 선택 정책은 유지한다. 장기 QA 담당과 독립 reviewer를 구분하고, 중요한 변경의 새 문맥 review는 기존 위험도·사용자 요구에 따라 사용한다.

검사는 작업 중 매번 전체 문서를 읽는 루프가 아니라 **현재 대상과 판단 지점에 맞춰** 수행한다.

- 기획·설계 중: 원본/링크 충돌과 필요한 미정 사항을 진단하되 아직 작성 중인 관련 설계가 있다는 사실 자체로 대화를 중단시키지 않는다. 구현 착수 판단에서는 해당 범위 계약·인수조건·시험 방법의 부족을 차단한다.
- 구현: 담당 테스트와 영향 회귀, 공통 계약/보안의 영향을 확인한다. 문서 표현만 바뀌었다고 동일 제품 테스트를 반복하지 않는다.
- 인수 검증: 합의한 통합 업무 흐름과 필요한 보안·회귀/UI/API/E2E를 실제 실행한다. 필수 Fail/Not Run/environment_blocked는 그대로 남긴다. 영향 외 미완료 의무도 전체 릴리즈 판단에서 숨기지 않는다.
- 소스·시험·의존성·환경·명령과 결과가 현재 대상에 맞고 증거가 확인된 경우만 기존 결과를 재사용한다. 개별 worker self-check만으로 전체 인수를 대체하지 않는다. 사용자/고객이 재실행을 요구하면 유지한다.

## 6. Runtime 변경 설계

### 6.1 상태 원본과 호환

MVP 제안은 프로젝트 `session.json`에 `process_model: product-iterative-v1`을 명시하고, 기존 `current_gate` 필드를 현재 구간의 **유일한 원본**으로 재사용하는 것이다. 값은 `planning`, `impl`, `acceptance`, `completed`로 구분한다. 사용자에게는 기획·설계/구현/인수 검증/이번 변경 완료로 표시한다. `completed`는 네 번째 작업 구간이 아니다.

`gate_status`는 새 모델에서 세 구간의 현재 작업 상태만 표현하고, 과거 Gate 승인/실행은 출처와 함께 보존한다. 레거시 Gate 1~5를 가짜 done으로 만들어 새 상태와 동시에 관리하지 않는다. `current_stage` 같은 두 번째 현재 상태 필드도 추가하지 않는다.

`process_model`이 없는 기존 Product는 legacy 운영을 유지한다. profile 이름이나 도구 버전만으로 상태를 재해석하지 않는다. 지원하지 않는 모델은 새 읽기/쓰기 경로에서 명확히 진단하고 상태 변경을 거부한다. 기존 구버전 도구가 이 표식을 이해한다고 가정하지 말고 이행 전에 총괄·열린 담당 작업·Dashboard의 지원 버전을 확인한다.

현재 작업 범위는 기존 작업/이슈/PR과 관련 원본을 참조한다. 후속 상태 구현에서는 **이 참조와 기준 revision을 승인·진행·검증에서 같은 대상으로 식별**해야 한다. 자유로운 `feature` 제목이나 브랜치명만으로 과거 승인/증적을 연결하지 않는다. 정확한 직렬화는 상태 구현 PR에서 기존 승인/소스 식별 API와 함께 고정하며 별도 수동 관리 문서를 만들지 않는다.

아래는 2026-09-11에 읽은 기존 코드다. 이 설계 PR에서 수정하지 않는다.

| 위치 | 현재 결합 / 바꿀 책임 |

`status`는 기본 조회 진입점으로 유지한다. `status --check`는 현재 범위의 다음 판단에 필요한 검사를 보여주며 상태나 승인 기록을 바꾸지 않는다. 상세 진단 CLI는 필요할 때 사용한다. 단계 이름 수만큼 새 facade를 추가하거나 기획·설계 안에서 여러 Gate 명령을 자동 실행하는 방식은 채택하지 않는다. 정확한 변경 명령 문법은 상태 구현과 함께 검증할 후속 계약이다.

### 6.3 기존 프로젝트 이행

`upgrade`는 지원 도구/지침을 설치하되 기존 프로젝트 상태와 승인 원본을 자동 전환하지 않는다. 먼저 읽기 전용 차이 보고서에서 다음 후보를 보여주고 사용자와 이행 범위를 합의한다.

| 기존 위치 | 새 구간 후보 | 자동으로 인정하지 않는 것 |
| --- | --- | --- |
| Phase 0/Gate 1/Gate 2/Gate 3 | 기획·설계 | 기존 단계의 일부 완료를 전체 구현 준비·허가로 간주하지 않음 |
| Impl | 구현 | 현재 범위/계약과 연결되지 않은 구현 허가 |
| Gate 4/Gate 5 | 인수 검증 | 기존 QA 상태만으로 수용 또는 배포 승인 간주 |
| completed | 이번 변경 완료 후보 | 당시 수용 범위/소스와 현재 변경이 일치한다는 추정 |

사용 중인 worker/쓰기 작업을 먼저 정리하고, dirty/미추적 파일·미완료 Run·승인/검증 기준·사용 도구 버전을 확인한다. 이행 도구는 원본과 상태 스냅샷을 보존하고, 전체 검증 후 상태를 원자적으로 적용해야 한다. 승인 근거가 불완전하면 보류/재확인으로 남기고 값을 만들어 채우지 않는다. 이행 전후 원본 문서·코드·시험 결과·Git 이력 보존을 비교한다.

이행 실패 시 이전 상태를 보존한다. 새 모델로 작업한 이후에는 예전 스냅샷을 덮어써 되돌리지 않는다. 초기 MVP는 진행 중인 실제 프로젝트 전환보다 새 합성 프로젝트 opt-in 검증을 먼저 수행한다. 일반 `init` 기본값 변경은 소비자/회귀 검증을 통과한 뒤 한다.

## 7. 구현 순서와 완료 기준

| 순서 | 범위 | 확인 기준 |
| --- | --- | --- |
| 0. 이번 설계 | 세 구간, 권한/문서/반복, [운영 시나리오](PRODUCT-ITERATIVE-PROCESS-SCENARIOS.md), 코드 영향 | 모순·누락을 검토. 런타임 테스트 통과로 표현하지 않음 |
| 1. 상태 모델과 계약 테스트 | legacy/new 구분, 현재 범위/승인 기준의 단일 식별, 반복 전환, 읽기 전용 status, 알 수 없는 모델 처리 | 준비와 허가 구분, 과거 승인 재사용 차단, Audit/PoC·legacy 불변. 아직 기본 활성화하지 않음 |
| 2. Product 검사와 운영 연결 | 범위별 준비/인수/릴리즈 검사, 코드 존재·과거 증적 처리, branch/QA/release 소비자, Core/선택 양식·Codex/Gemini, Dashboard schema/UI | CLI와 역할 지침/화면이 같은 상태 모델 사용. 기존 7단계를 뒤에서 요구하지 않음 |
| 3. 합성 반복 파일럿 | 신규 기능, 확장, 결함·업무 변경·환경 차단, 완료 후 다음 범위, legacy 이행 dry-run/보존 | 사례별 기대 행동을 실행으로 확인. 문서 현재성·추적·필수 QA와 사용자 허가 유지 |
| 4. 실제 적용 판단 | 파일럿 결과 검토 후 새 init 기본값과 명시 이행의 적용 범위 결정 | 범위별 원본/승인/증적 보존과 소비자 호환이 입증된 범위만 활성화 |

구현은 branch/PR 단위로 검증하며 상태 엔진만 바꾼 중간 산출물을 운영 지침만으로 실제 프로젝트에 적용하지 않는다. 전체 AC/REQ 목록 조회는 원본 탐색의 별도 후속 과제로 유지하지만 3구간 시나리오 설계의 선행 조건으로 만들지 않는다.

2026-09-11 단계 2a: [범위별 문서·실행 증적 검사](PRODUCT-PROCESS-CONTRACTS.md#41-범위별-검사-연결-단계-2a)를 실험 세션의 `status --check`에 연결했다. 기획 중 Planned 시험과 인수 시 필수 실행을 구별하며 검사/승인/릴리즈는 별개로 표시한다. 아직 상태 저장 CLI, QA 실행 경로, Dashboard 및 init/upgrade 기본 활성화는 연결하지 않았다.
