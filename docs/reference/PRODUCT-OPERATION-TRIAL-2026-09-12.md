# Product Operation Trial: 2026-09-12

## 목적과 범위

PR #42 병합 후 기능 추가를 잠시 멈추고, Run 없는 QA 전달/실패/수정/재시험/결과 회수의 운영 부담을 관찰한다. 프레임워크의 필수 산출물이나 에이전트 시작 문서가 아니다.

- 기준: main `12a6e69`, [PR #42](https://github.com/zeni-on/vulcan-anvil-ex/pull/42).
- 대상: [기존 실행 fixture](../../scripts/regression/product_execution_fixture.py)로 새로 만든 독립 로컬 프로젝트. 원본 문서 예시나 PMTool은 변경하지 않는다.
- 사용자 합의: 같은 요청을 보완해 재제출하며 반려 당시 내용과 사유를 보존한다. [대화 원본](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md)을 따른다.
- 작성자만/반려 상태에서만 재제출한다는 조건은 fixture 가정이다. 미정인 실제 검토자 권한/보존 기간을 승인한 것으로 해석하지 않는다.
- 승인 actor와 권한은 합성 시험 데이터다. `completed` 확인은 상태 계약 시험이며 실제 제품 인수나 릴리즈가 아니다.

## 관측 방법

Python 표준 라이브러리 fixture를 사용한다. 의존성 설치, UI, 서버, 외부 서비스, 새 QA worktree는 필요 없다. 처음부터 알려진 이력 보존 결함이 들어 있으므로 그 실패를 새로운 Ex 결함이나 자연 발생 결함 발견률로 세지 않는다.

새 문맥의 native QA 담당자에게 계약/시험 계획/시험 코드와 정확한 실행·출력 경로를 전달한다. 총괄은 별도 보고 정리 중 결과를 기다리고, 실패 후 허가된 코드 한 줄만 수정한다. 재시험은 같은 담당자에게 새 증적 경로로 맡긴다. 문서 보정 때문에 제품 시험을 반복하지 않는다.

로컬 관측 helper가 기존 fixture/CLI를 호출하고 명령 시간·종료 코드·출력량을 기록한다. 이는 이번 실험의 준비 도구이지 Ex가 제공하는 운영 자동화가 아니다. helper 제작, 상태 요청 조립, 모델 대기 비용을 명령 실행 시간에 숨겨 전체 소요시간으로 보고하지 않는다. 사용자 로컬 경로/전체 대화/원본 로그는 공개 저장소로 복사하지 않는다.

## 실행 결과

첫 실행의 실제 로그는 REG-001 Fail, REG-002/SEC-REG-001 Pass였다. 원문 대신 수정 내용을 이력에 저장하는 assertion이 실패했으며, 해당 시험의 뒤쪽 원본 불변 assertion은 아직 실행되지 않았다. 실패 결과 요청은 거부됐고 session bytes는 그대로였다. 총괄이 합성 fix 허가로 impl에 돌아가 이력에 `request["content"]`를 기록하도록 한 줄 수정한 뒤 acceptance로 복귀했다.

같은 담당자가 재시험을 한 번 수행했고 실제 로그는 3건 모두 Pass/exit 0이었다. 총괄은 새 JSON/log를 읽고 ID별 결과를 채웠다. 성공 결과만 제출한 미리보기는 `missing scoped accept decision`으로 차단됐고, 해당 결과의 합성 accept 결정을 연결한 요청만 `completed`로 저장됐다. 최종 `status --check`는 ready/이슈 0건, `release_authorized: false`였다. 원본 계약/시험 정의/시험 코드는 변경하지 않았으며 계획의 Planned도 그대로 유지했다.

별도의 총괄 함수 호출에서는 사용자가 합의한 대화 예시를 직접 넣었다. `장비 필요` / `수량을 알려주세요`에서 `장비 2대 필요`로 보완했을 때 동일 ID 7, 최신 내용 변경, 당시 원문·사유 보존, 입력 객체 불변을 assertion으로 확인했다. 함수 수준 결과이며 화면/DB 저장/실제 검토자 업무까지 확인한 것은 아니다.

첫 함수 호출의 한글 stdout은 터미널 수집 과정에서 깨져 보였다. JSON Unicode escape로 출력하는 짧은 호출을 한 번 더 수행해 문자열을 확인했다. 실제 unittest 전체를 다시 돌리지는 않았다. QA 첫 shell의 Starship 경고도 제품 실패로 바꾸거나 제거하려고 재시험하지 않았다.

위임 식별: native `worker` Aristotle, `01a093b9-9b80-7e01-a73b-c43b782decb3`. 새 문맥으로 한 번 생성하고 동일 담당자에게 재시험 한 번을 보냈다. 모델 override는 생략하고 effort medium을 요청했으며 실제 런타임 모델/effort를 별도로 인증하지 않았다. verify-only 범위를 유지하고 회수 후 담당자를 종료했다.

로컬 원본은 독립 예시의 `evidence/`에 남겼다: `initial.json/.log`, `retest.json/.log`, `handoff-initial.json`, `handoff-retest.json`, `return-initial.json`, `return-retest.json`, `preview-initial.json`, `preview-retest.json`, `final-status.json`, `operation-cli.jsonl`. 전달/반환/preview 사본과 계측 JSONL은 이번 관측 자료이며 프로젝트마다 이 파일들을 추가하도록 요구하지 않는다. 실패 로그를 새 성공 로그로 덮어쓰지 않았다.

| 제품 시험의 불필요한 재실행 | 문서/경고 정리로 인한 전체 재시험 0회 | 별도 총괄 함수 관측 2회는 위 시험 횟수에 포함하지 않음 |

운영 CLI 10회는 `execute --dry-run` 2회, `execute --verify` 2회, `session` preview 2회/apply 3회, 최종 `status --check` 1회다. 실제 시험 종료 코드와 원본 로그를 총괄이 대조하는 검토는 필요하며, 그 자체를 불필요한 중복 시험으로 세지 않는다.

총괄의 프레임워크 가이드/fixture 탐색 전체와 자동 내부 파일 읽기는 계측하지 않았다. 따라서 모든 역할에서 문서 재조회가 줄었다고 주장할 수 없다. 토큰/크레딧 계측과 대조군도 없으므로 비용 절감률이나 모델 간 우열을 주장하지 않는다.

## 판단과 다음 초점

**이 좁은 흐름에서는 새 Run과 반복 self-check 없이 검증 경계가 작동했다. 다만 일반 운영이 충분히 가벼워졌다는 결론은 이르다.**

1. 유지할 가치가 있는 부분: 업무 예시를 assertion으로 확인, 실패와 성공 증적 분리, 검증 권한과 수정/수용 권한 분리, 변경한 코드에만 관련 재시험 수행. 이번 trial에서 새 차단 결함은 관측하지 않았다.
2. 우선 줄여볼 부담: `return_request`를 받더라도 ID별 결과/명령/참조를 조립하고 preview의 수용 키를 연결하는 일이 남는다. 이번에는 로컬 helper가 이를 도왔으므로 사용자가 기본 CLI만으로 매끄럽게 운영했다고 보고해서는 안 된다. 결과 조립과 긴 JSON 해석은 개선 후보이며, 9.823초의 CLI 실행만으로 전체 지연 원인을 확정할 수는 없다.
3. 다음 작업의 경계: 새 CLI/Gate/필수 문서를 추가하기보다 기존 전달/반환 경로에서 중복 입력을 줄일 여지를 먼저 검토한다. 실제 결과 해석과 수용 결정은 자동 Pass/자동 승인으로 대체하지 않는다. 이번 PR은 관측 보고와 로드맵만 변경한다.
4. 그 다음: 미정인 업무 권한/이력 정책을 합의한 같은 제품의 실제 화면·저장·통합 시험과 CI 연결을 검증한다. 현재 함수 fixture 결과로 UI 품질, 지속 저장, 동시성, Agy runtime, 일반 init/upgrade 이행, 발행 성공이나 실제 사용자 만족도를 입증하지 않았다.

기능 추가를 잠시 멈추고 운영 비용을 먼저 보자는 방향은 유지한다. [제품 CI 설계](PRODUCT-CI-AND-QUALITY-LOOP.md)와 [기존 실행 검증 이력](PRODUCT-PROCESS-EXECUTION-VERIFICATION.md)은 참고 자료로만 연결하며 새 필수 입력으로 만들지 않는다.
