# Product CI And Quality Loop

- 상태: 2026-09-12 설계 / Product 샘플 적용 전
- 범위: Product의 업무 예시, 실행 가능한 검증, CI, 인수 판단 연결
- 선행 작업: [3구간 운영 연결](PRODUCT-PROCESS-CONTRACTS.md), [업무 합의 파일럿](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md)

이 문서는 적용할 방향과 시험 기준이다. 현재 Core 정책, init/upgrade, CI 설정, 저장소 보호 규칙을 변경하지 않는다. 일반 Product 프로젝트의 필수 검사로 활성화한 상태가 아니며 Audit/PoC에도 소급 적용하지 않는다.

## 1. 목적과 현재 차이

목표는 코드·문서 정합성뿐 아니라 **합의한 업무가 실제 제품에서 끝까지 되는지 반복 확인**하는 것이다. CI는 그중 자동 실행 가능한 검증을 담당한다. CI 성공, 사용자 수용, merge·릴리즈·배포 허가는 서로 다른 판단이다.

| 현재 확인한 것 | 아직 없는 것 |
| --- | --- |
| Ex 저장소의 [Regression Smoke](../../.github/workflows/regression-smoke.yml)가 Python 회귀와 Dashboard 정적 검사·빌드·테스트를 실행 | init으로 생성되는 각 제품의 CI 자동 연결 |
| Product의 요구/계약/시험 원본 연결과 실제 검증 결과 검사 | 각 제품의 스택·업무에 맞는 CI 필수 검사 선정·실행·통합 차단 |
| [업무 분석 가이드](PRODUCT-DISCOVERY-AND-VALIDATION-GUIDE.md)와 요청 보드 대화 연습 | 한 업무 흐름의 합의부터 실제 제품 시험까지 완주한 파일럿 |
| 실험 Product의 상태·범위·허가, 검증 실행, 릴리즈 미리보기 | 남은 운영 연결과 일반 활성화, 실제 발행 권한 계약 |

Ex 자체의 CI 통과를 생성된 제품의 품질 증명으로 사용하지 않는다. 체크 명령은 계약·파일·실행 결과를 확인하지만 업무 의미의 완전성을 증명하지 않는다.

## 2. 적용할 최소 원칙

- **CI 도구명이 아니라 자동 검증 능력을 기준으로 한다.** GitHub 프로젝트의 첫 샘플은 GitHub Actions를 사용한다. 조직의 Jenkins 등 기존 CI가 있다면 같은 기준을 연결하고 이중 파이프라인을 강제하지 않는다.
- 로컬과 CI가 같은 프로젝트 스크립트/테스트 설정을 호출한다. 명령 구현은 manifest·스크립트·도구 설정이 원본이고, 개발 가이드는 호출 방법·적용 범위·성공 기준과 링크를 설명한다. 여러 문서에 스크립트 본문을 복제하지 않는다.
- 해당 스택의 정적 분석, 빌드 또는 실행 가능성 검사, 업무 동작 테스트를 선정한다. 없는 프론트엔드에 UI 테스트를 요구하거나 모든 분석 도구를 일괄 설치하지 않는다.
- 필수 동작 검증은 실제 실행 결과로 확인한다. 파일 존재, 종료 코드 0, 스크린샷 생성만으로 충분하다고 간주하지 않는다. 테스트 발견 수와 필수 시나리오 실행 여부도 확인한다.
- 실패·필수 검증 누락·환경 차단은 숨기지 않는다. 모든 warning을 0개로 만드는 정책이나 고정 coverage 백분율을 새 기본값으로 두지 않는다.
- 검사를 통과하려고 기대값을 낮추거나 실패 무시 옵션을 붙이지 않는다. 요구 변경에 따른 정당한 테스트 변경은 가능하며, 변경 이유·영향을 검토한다.
- 새 Gate/Run, Git SHA 증적 칼럼, 별도 CI 원장을 추가하지 않는다. 기존 테스트 정의, 결과 요약과 CI 실행/리포트 링크를 사용한다.

## 3. 3구간에서 수행할 일

| 시점 | 담당과 행동 | 확인할 결과 |
| --- | --- | --- |
| 기획·설계 | 사용자와 총괄이 업무 목적·대표/중요 예외를 합의. 기술 담당은 스택에 맞는 명령·환경·필수 검사 선정 | 관측 가능한 AC, 시험 방법, 아직 미정인 업무 질문. CI나 구현 승인으로 바꾸지 않음 |
| 구현 환경 준비 | 구현 담당이 실행 스크립트·설정과 CI 후보 연결. 기존 프로젝트 CI가 있으면 재사용 | 로컬 재현 가능, 의존성 설치·테스트 발견·빌드 가능. workflow 파일만 만든 상태와 구분 |
| 첫 코드 통합 PR | 해당 PR에서 실제 CI 실행. 총괄은 필수 job과 업무 테스트가 실행됐는지 확인 | 실패/누락/환경 차단이 있으면 코드 통합 보류. PR 생성이나 검토 자체를 금지하는 것은 아님 |
| 후속 변경 | 영향 범위와 공통 회귀 기준에 따라 같은 파이프라인 실행 | 새 기능은 시험 추가, 바뀐 계약은 시험 현행화. 표현만 바꾼 문서 작업은 근거 있는 비적용 처리 가능 |
| 인수 검증 | 품질 담당이 통합된 제품의 업무 흐름·중요 예외를 확인하고 총괄이 사용자에게 결과 제시 | CI 증적 재사용 가능 여부와 남은 수동 확인을 구분. CI green을 사용자 수용으로 해석하지 않음 |
| 수용 후 출시 | 이미 합의된 release/merge 권한과 저장소 정책 적용 | 범위 수용만으로 자동 push/merge/deploy하지 않음 |

환경·소스·시험 정의가 바뀌었으면 영향에 따라 재시험한다. 같은 유효한 결과를 문서 정리 횟수만큼 재실행하거나, 단순 staging/commit 때문에 무효화하지 않는다. CI가 제공하는 PR/실행 대상 정보로 다른 변경의 결과를 잘못 가져오지 않았는지 확인하며, 이를 수동 Git 증적 작성 의무로 확대하지 않는다.

## 4. 성공과 차단 판정

아래 상태명은 설계상의 설명이며 새 필수 JSON/YAML 스키마가 아니다.

| 관측 | 판단 | 후속 |
| --- | --- | --- |
| 필수 명령 성공, 필요한 테스트가 발견·실행되고 기대 동작 충족 | 해당 검사 통과 | 인수의 나머지 조건·사용자 수용은 별도 확인 |
| lint/type 오류, 빌드 실패, 업무 assertion 실패 | 실패 | 원인·영향과 재현 결과 반환, 허용된 수정 후 재검증 |
| 필수 명령/보고서 없음, 테스트 0개, 필수 시나리오 누락 또는 skip | 미실행/누락 | green으로 집계하지 않고 보완 |
| 의존성·브라우저·서비스·권한 부족 | environment_blocked | 제품 결함과 구분하고 환경 해결. 자동 Pass/제외 금지 |
| queued/running, 취소·timeout, 결과 조회 불가 | 미확인 또는 미완료 | 필수 통합 판정 보류. 이전 실행 성공으로 대체하지 않음 |
| 합의된 범위상 비적용 | not applicable | 사유·적용 경계 확인. 필요한 테스트 실패를 비적용으로 바꾸지 않음 |
| 명령은 통과했으나 비차단 warning 존재 | 결과와 warning을 함께 보고 | 위험 수준에 따른 개선. warning 자체를 무조건 차단하지 않음 |

GitHub required status checks는 `successful`, `skipped`, `neutral`도 허용한다. 따라서 브랜치 보호 설정만으로 “필수 검사가 실제 실행됨”이 보장되지는 않는다. [GitHub 브랜치 보호 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

샘플에서는 항상 실행되는 최종 품질 job이 필요한 하위 job의 실행/성공 여부를 집계하도록 시험한다. 관련 있는 필수 job의 skip·누락·취소·실패는 최종 성공으로 바꾸지 않는다. 문서 전용 등 비적용 분류는 영향 기준을 별도로 검증하며, CI/검사 설정 변경 자체를 무검증 문서 변경으로 분류하지 않는다. 기존 CI가 같은 판정을 제공하면 별도 집계기를 중복 구현하지 않는다.

workflow 전체가 시작되지 않으면 그 안의 최종 job도 판정할 수 없다. 통합 시점에는 예상한 required check 자체의 부재를 별도로 확인하고 보류한다. trigger/path 필터로 전체 실행이 빠지는 경우도 시험하며, 집계 job 하나로 모든 누락이 해결됐다고 주장하지 않는다.

테스트 수가 1 이상인 것만으로도 충분하지 않다. 필수 업무 시나리오가 빠졌는데 무관한 테스트만 통과하는 경우를 시험 계획/실행 결과와 함께 확인한다. runner마다 수집/skip/실패 형식이 다르므로 첫 샘플의 runner부터 연결하며, 모든 언어의 보고서 파서를 Ex에 먼저 만들지 않는다.

## 5. 문서·도구 책임

| 정보 | 원본/책임 | 중복시키지 않을 것 |
| --- | --- | --- |
| 해결할 문제, 업무 규칙과 기대 결과 | 기존 업무/요구·AC 원본, 사용자·총괄 | CI 문서에 요구 전문 복사 |
| 검증 진입점과 실행 구현 | package script, build tool, 테스트/분석 설정, 구현 담당 | 문서마다 별도 버전의 명령 구현 |
| 실행 방법·환경·필수/비적용 기준 | 기존 [Engineering Guide 양식](../templates/product/PRODUCT_ENGINEERING_GUIDE_TEMPLATE.md)의 프로젝트 원본 | 새 CI 필수 문서/ID 체계 |
| PR 실행 조건과 job 연결 | `.github/workflows/` 또는 Jenkinsfile 등 | 로컬과 다르게 수동 재구현한 검증 절차 |
| 실제 결과·실패·환경 차단 | 기존 시험 결과/회귀·릴리즈 요약에서 원본 리포트 링크 | CI 로그 전문을 Markdown에 반복 붙이기 |
| 통합 보호 | 저장소 관리자가 승인한 required checks/동등 통제 | 에이전트의 무허가 저장소 설정 변경 |

Core에 기준을 채택할 때 Codex/Gemini는 그 원본으로 라우팅한다. 각 adapter에 별도 CI 방법론을 복제하지 않는다. 초기에 `status --check`는 로컬에서 알 수 있는 설정/누락과 실제 검증 여부를 구분하고, 원격 결과 조회 실패를 제품 실패나 성공으로 추정하지 않는다. PR의 실제 CI 결과와 required checks는 통합 시점에 확인한다. 새 CLI 이름을 먼저 추가하지 않는다.

## 6. 보안과 호환 경계

- 샘플 workflow의 기본 권한은 읽기로 제한한다. 외부 PR 코드에 secret이나 운영 자격증명을 제공하지 않고, 신뢰하지 않는 코드를 실행하는 job에 쓰기 권한을 주지 않는다. 분석·빌드·시험에 운영 배포를 섞지 않는다.
- 외부 PR의 artifact·캐시도 신뢰하지 않는 입력으로 취급한다. 후속 권한 있는 workflow에서 이를 실행하거나 보호된 캐시로 승격하지 않으며, 로그/리포트에 secret·개인정보를 남기지 않는다. 보관·공개 범위도 확인한다. [GitHub Actions 보안 사용](https://docs.github.com/en/actions/reference/security/secure-use)
- 필요한 의존성·브라우저·서비스를 선언하고 캐시 miss도 시험한다. 개발자 PC의 설치 상태를 CI가 그대로 상속한다고 가정하지 않는다. 사내 자원 때문에 self-hosted runner를 쓰면 관리·격리·정리 책임을 별도로 정한다.
- lint/typecheck 등 정적 분석과 CodeQL 같은 보안 분석은 같은 기능이 아니다. 저장소 공개 범위·GitHub 요금제/Code Security 이용 가능 여부를 확인한다. 특정 유료 제품 구매를 Product의 필수 조건으로 삼지 않는다.
- 저장소 보호 규칙 적용에는 관리자 권한·요금제·조직 정책 확인이 필요하다. 실행 job의 고유 이름, required check, 관리자 우회 정책을 합의한 뒤 설정한다. workflow 커밋만으로 merge가 기술적으로 차단됐다고 보고하지 않는다.
- 기존 프로젝트의 workflow·Jenkinsfile·승인 문서는 upgrade로 덮어쓰지 않는다. 먼저 현재 도구와 기준을 점검하고 명시적 도입 변경으로 연결한다. CI가 없는 기존 제품을 upgrade만으로 갑자기 진행 불가로 만들지 않는다.

## 7. 적용 순서와 파일럿 시험

1. **이번 변경: 설계와 우선순위 고정.** 이 문서와 로드맵, 업무 파일럿의 시험 후보를 연결한다. runtime/기존 프로젝트 변경은 없다.
2. **선행: Product 운영 연결과 업무 합의.** [프로세스 계약](PRODUCT-PROCESS-CONTRACTS.md)의 남은 branch/QA 위임·결과 회수/발행 권한·라우팅을 좁은 단위로 검증한다. 동시에 요청 보드의 중요한 미정 업무를 확인하고 한 흐름의 REQ/AC·시험 후보를 확정한다. 발행 권한 설계는 실제 발행 지시가 아니다.
3. **같은 합성 제품에 CI 연결.** 로컬 제품 테스트를 구현·실행한 후 GitHub Actions에서 같은 진입점으로 실행한다. 외부 서비스나 PMTool을 대신 변경하지 않는다. 로컬 unit으로 workflow를 읽은 것과 GitHub에서 실제 실행한 것은 별도 결과로 기록한다.
4. **통과·실패 경계 검증 후 Product 기준 채택.** 아래 사례를 관측하고 Core/선택 양식/adapter와 필요한 검사만 보강한다. 일반 프로세스 활성화와 기존 프로젝트 도입 여부는 그 결과를 보고 따로 결정한다.
5. **후속: 운영 결과 피드백.** 실제 사용 후 업무 지연·누락 등 해당 제품의 문제 지표를 다시 본다. 새 대시보드·원격 수집·성과 수치를 먼저 만들지 않는다.

| 샘플 시험 | 입력/행동 | 기대 관측 |
| --- | --- | --- |
| 정상 파이프라인 | 현재 범위의 정적 검사·빌드·업무 시험 실행 | 필요한 job/시나리오 실행·성공과 리포트 확인. 수용/배포는 자동 처리 안 됨 |
| 실제 업무 결함 | 보완 재제출이 이전 반려 내용을 덮어쓰도록 결함 주입 | 코드 문법/빌드가 통과해도 이력 보존 assertion이 실패 |
| 검사 약화 | 실패 무시, assertion 제거/무조건 성공으로 변경 | 알려진 결함 재주입 시 검증력 상실을 확인하고 설정·시험 변경 검토에서 거부. 임의 약화를 모두 자동 탐지한다는 보장은 아님 |
| 테스트 누락 | 테스트 탐색 경로 변경, 0건 실행, 필수 사례 skip | 종료 코드만 보지 않고 최종 품질 job 실패/미완료 |
| 환경 차단 | 브라우저/의존성/서비스 준비 실패 | 환경 차단 구분, 필수 검증 통합 보류. 업무 결함으로 오기하지 않음 |
| 실행 중단 | 필수 job 취소·timeout 또는 결과 조회 불가 | 필수 성공으로 집계하지 않음 |
| workflow 전체 누락 | trigger/path 필터로 파이프라인이 시작되지 않음 | 예상 required check 부재로 통합 보류. 집계 job 실행 여부까지 확인 |
| 잘못된 skip | CI 파일을 수정하거나 공통 코드 변경을 문서 전용으로 분류 | 필수 검사 생략/최종 green 방지 |
| 문서만 변경 | 업무 의미·검사 설정 변화 없는 설명/링크 수정 | 합의된 영향 기준에 따른 검사. 업무 테스트 무조건 반복 금지 |
| 다른 CI/기존 프로젝트 | Jenkins 사용 또는 이미 있는 workflow와 승인 원본 | 동등 기준 연결, 이중 실행·자동 덮어쓰기 없음 |

위 표는 실행 계획이며 Pass 기록이 아니다. 실제 샘플 결과에는 실행한 범위·실패를 발견한 근거·미실행/남은 한계를 나누어 적는다. 모든 프로젝트의 CI 연결·브랜치 보호·업무 적합성이 자동 보장된다고 표현하지 않는다.

## 8. 참고와 적용 범위

- [영상: AI 시대의 코드 품질](https://www.youtube.com/watch?v=3JDqfWGKoiY): 1:17 이후 업무 문제/결과, 4:35 이후 알림 기능의 시스템 관점, 8:43 이후 실행 가능한 기준과 CI, 10:27 이후 지속 품질 관점을 참고했다. 엔지니어링 의견이지 Ex의 효과를 실증한 자료나 의무 표준은 아니다.
- [GitHub Actions 개요](https://docs.github.com/en/actions/get-started/understand-github-actions): 이벤트에 따른 workflow/job 실행. Actions가 테스트나 업무 인수조건을 대신 작성하는 것은 아니다.
- [Jenkins Pipeline](https://www.jenkins.io/doc/book/pipeline/): Jenkinsfile로 버전 관리하는 실행 단계. GitHub Actions만을 요구하지 않는 근거다.
- [GitHub 브랜치 보호](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches): required checks, 상태와 보호 규칙의 제공/우회 조건 확인.
- [GitHub Actions 보안 사용](https://docs.github.com/en/actions/reference/security/secure-use), [self-hosted runners](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners), [code scanning](https://docs.github.com/en/code-security/concepts/code-scanning/code-scanning): 권한·실행 환경과 분석 기능의 적용 조건 확인.

공개 문서는 2026-09-12 확인했다. 실제 적용 시 저장소 권한·조직 정책·요금제와 사용 action/도구 버전을 다시 확인한다. 이 문서는 정식 표준 준수 인증이나 특정 제품의 보안 보장이 아니다.
