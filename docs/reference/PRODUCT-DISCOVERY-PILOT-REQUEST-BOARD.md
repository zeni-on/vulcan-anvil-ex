# Product Discovery Pilot: Request Board

- 상태: 대화 연습 진행 중 / 기존 제품 변경 아님
- 작성일: 2026-09-10
- 진행 기준: [Product Discovery And Validation Guide](PRODUCT-DISCOVERY-AND-VALIDATION-GUIDE.md)

## 1. 목적과 범위

문서 예시 프로젝트 `sample-ex-product-docs-0910-1`의 가상 팀 요청 보드로 업무 질문부터 요구 도출까지 연습한다. 고객 자료나 PMTool 업무를 사용하지 않는다. 실제 서비스·구현·QA 증적은 없으며, 예시의 초안도 사용자 승인 기준선이 아니다.

이번 연습에서는 기존 파일을 읽고 변경 후보만 이 문서에 남긴다. 예시 프로젝트의 요구/설계/시험 원본, 코드, Gate 상태는 변경하지 않는다. 연습 중의 업무 답변이 실제 제품 변경이나 전체 Gate 승인으로 자동 적용되지 않는다.

## 2. 출발 자료

읽은 기준은 예시 프로젝트 커밋 `a84565a`다. 아래 경로는 예시 프로젝트 루트 기준이며 Ex 저장소에 해당 산출물을 복사하지 않는다.

| 원본 | 연습에서 읽은 내용 |
| --- | --- |
| `docs/product/PRODUCT_BRIEF.md` | 채팅에 흩어진 요청을 등록·결정·조회하는 목적. 요청자/검토자, SCN-001~004 |
| `docs/artifacts/01-requirements/requests.md` | 요청 등록, 한 번의 승인/반려, 권한별 조회. REQ-001~003, AC-001~006 |

현재 초안의 핵심은 요청자는 자기 요청을 보고, 검토자는 본인 작성이 아닌 pending 요청을 결정하며, 결정 후 변경·중복 처리는 거부한다는 것이다. 반려 후 보완·재제출의 별도 경로는 정의되어 있지 않다.

이 자료는 대화 출발점이지 검증된 실제 업무 조사 결과가 아니다. 아래 진행 순서는 **기존 초안이 있는 프로젝트의 빈틈을 점검하는 연습**이다. 새 프로젝트에서는 먼저 문제·사용자·경계를 확인하고, 이 보드의 역할·상태를 기본값으로 주입하지 않는다.

## 3. 먼저 발견한 질문

> 반려된 요청은 어떻게 다시 신청할 수 있어야 할까?

기존 초안만 구현하면 등록·결정·조회 AC는 충족하면서도 보완 제출이 필요한 업무는 끝낼 수 없을 수 있다. 그렇다고 모든 요청 보드에 재신청을 임의로 추가할 수도 없다. 기능 누락인지 의도한 범위 제한인지는 사용자에게 확인할 문제다.

| 선택지 | 업무 의미와 확인할 영향 |
| --- | --- |
| 기존 요청을 보완해 재제출 | 같은 업무 건의 연속성 유지. 반려 후 편집·재검토 경로와 결정 이력 정책 필요 |
| 새 요청으로 다시 작성 | 기존 반려 건은 종결. 새 건과 이전 건의 연결·중복 업무 여부 확인 필요 |
| 이번 범위에는 재신청 없음 | 반려 후 업무가 종료되는지, 외부 절차로 넘기는지 확인 필요 |

## 4. 사용자와 확인한 내용

2026-09-10 대화에서 사용자가 **기존 요청을 보완해 재제출**을 선택했다. 이 연습에서 합의된 방향이다. 같은 요청의 업무적 연속성을 뜻하며 DB 테이블이나 이력 저장 방식까지 정한 것은 아니다.

영향 분석:

- 기존 REQ-002의 결정 후 변경 금지 문장을 무조건 유지할 수 없다. 반려 후 보완·재제출과 임의 결정 덮어쓰기를 구분할 필요가 있다.
- “한 번의 결정”이 요청의 전체 생애 기준인지 제출 회차 기준인지 구체화해야 한다. 회차 기준이라는 해석은 아직 제안이다.
- 재제출을 어디서 시작하는지, 다시 검토할 수 있는 사람, 기존 결과의 표시 방식이 달라질 수 있다.
- 승인된 요청까지 수정할 수 있다는 뜻은 아니다. 이미 있는 자기 요청 검토 금지 등의 공통 권한을 해제하는 답도 아니다.

같은 날 후속 질문에서 사용자는 **당시 내용과 반려 사유 모두 보존**을 선택했다. 따라서 보완한 최신 내용으로 이전 내용을 덮어 잃는 방식은 이 연습의 합의와 맞지 않는다. 기존 초안에 반려 사유 저장이 구현되어 있다는 근거는 없으므로, 보존 대상의 정의부터 변경 후보로 다룬다.

보존 기간, 조회 권한, 여러 번 반려될 때의 표시 방식은 아직 결정하지 않았다. 이 답을 무기한 보존이나 모든 사용자에게 이력을 공개하라는 승인으로 해석하지 않는다.

## 5. 규칙·예시·열린 질문

아래는 Example Mapping을 표로 연습한 것이다. 새로운 테스트 실행 결과나 승인된 상세 계약이 아니다.

| 종류 | 내용 | 근거/상태 |
| --- | --- | --- |
| 사용자 이야기 | 요청을 반려받은 사람이 내용을 보완하여 같은 요청을 다시 신청하고 싶다 | 사용자 선택 방향을 재진술 |
| 규칙 | 기존 요청을 보완해 재제출할 수 있다 | 이 연습에서 사용자 선택 |
| 규칙 | 반려 당시 내용과 사유를 함께 보존한다 | 이 연습의 두 번째 사용자 선택 |
| 구체적 예시 후보 | 민수가 등록한 장비 요청을 영희가 반려한다. 민수가 설명을 보완해 같은 요청에서 재제출하고, 검토 대상에 다시 나타난다 | 재검토 상태·권한·표시 방법 확인 필요 |
| 구체적 예시 후보 | 첫 제출의 설명은 '장비 필요', 반려 사유는 '수량을 알려주세요'다. 민수가 설명을 '장비 2대 필요'로 보완해 재제출해도 이전 설명과 반려 사유를 확인할 수 있다 | 두 사용자 선택에서 도출. 누가 어디서 볼지는 후속 확인 |
| 예외 예시 후보 | 다른 요청자가 민수 요청을 수정/재제출하려고 한다 | 기존 권한을 유지한다면 거부. 재제출 행위에도 동일 경계 적용 여부 확인 |
| 예외 예시 후보 | 재제출한 요청을 보면서 누군가 이전 화면으로 다시 처리하려고 한다 | 이전 결정과 새 제출을 혼동하지 않도록 할 정책 미정 |
| 열린 질문 | 작성자만 재제출할까? 검토자는 이전과 같아야 할까? | 후속 확인. 새 역할/담당자 제도를 임의 추가하지 않음 |
| 열린 질문 | 보완 중 내용은 누구에게 보이고, 어떤 시점에 다시 검토 대상이 될까? | 후속 확인. 새 상태 코드/저장 버튼을 아직 확정하지 않음 |
| 열린 질문 | 보존한 이력의 조회 범위와 보존 기간은 어떻게 정할까? | 기존 접근·데이터 정책과 함께 확인할 대상 |

다음 대화에는 모든 질문을 한꺼번에 던지지 않는다. 답이 온 부분의 흐름과 예시를 먼저 되짚고, 그 답으로 여전히 결과가 갈리는 질문만 이어간다. 단순 권장값을 조용히 확정 사실로 바꾸지 않는다.

### 5.1 사용자 답에서 도출한 인수조건 후보

아직 원본 AC 번호를 배정하거나 구현하지 않았다. 아래는 사용자 두 선택을 관측 가능한 문장으로 바꾼 후보다.

| 조건/행동 | 기대 결과 | 미정 경계 |
| --- | --- | --- |
| 반려된 요청의 내용을 보완하여 재제출 | 별개 업무 건으로 새로 신청하지 않고 기존 요청에서 보완한 제출 내용을 확인한다 | 재제출 권한, 상태·목록 표시 |
| 위 예시에서 설명을 '장비 2대 필요'로 바꿔 재제출 | 이전 설명 '장비 필요'와 반려 사유 '수량을 알려주세요'가 보존되며 최신 제출 내용과 구별된다 | 이력을 볼 수 있는 사람·위치·보존 기간 |

반복 반려·동시 수정·이력 접근 예외까지 합의한 것은 아니다. 구체적 입력과 기대 결과가 작성되었어도 실행한 테스트가 아니므로 Pass로 표시하지 않는다.

## 6. 요구·설계·시험으로 연결할 후보

| 관점 | 후속에 확인할 변경 후보 | 지금 하지 않은 것 |
| --- | --- | --- |
| 목표·시나리오 | 요청 처리 흐름에 반려 후 보완·재검토 분기를 포함할지, 성공 기준에 어떻게 반영할지 | 전체 업무 흐름 승인 |
| REQ/AC | REQ-002의 종결/재제출 경계와 권한·중복 처리의 적용 범위. 관측 가능한 정상/예외 AC | 새 ID 배정, 기존 AC 자동 덮어쓰기 |
| UI/API | 재제출 가능 시점과 동작, 이전 결정 표시, 오래된 화면의 행동 | 엔드포인트/화면/상태 코드 확정 |
| 데이터·보안 | 사용자 답에 따른 이전 내용/사유 보존, 접근권한, 재제출 이력의 의미 | DB 설계·민감정보 보존 기간 확정 |
| 시험 계획 | 반려, 보완, 재제출, 재검토까지의 통합 흐름과 권한/중복 예외 | 테스트 수행, Pass 기록 |

연습의 합의가 실제 변경으로 채택될 때만 기존 원본에 반영한다. 승인된 프로젝트였다면 기존 변경 관리와 영향 Gate 판단을 따른다. 이미 정의한 공통 권한과 오류 계약을 시나리오별로 복제하지 않는다.

## 7. 현재 결과와 다음 확인

- 완료: 공개 가이드와 연결한 진행안, 출발 자료 읽기, 재신청 의미 공백 확인, 사용자 두 선택, 기존 규칙과의 영향 비교, 인수조건 후보 두 개.
- 진행 중: 대표 예시의 되짚기와 미정 경계 확인. 재제출 권한·상태·종료 조건까지 합의한 완결된 업무 흐름은 아직 아니다.
- 미수행: 완성된 시나리오/REQ/AC 검토, Core·adapter·템플릿 배포, CLI/전체 AC 목록 구현, 실제 제품 변경과 QA.

다음은 대표 한 건을 처음부터 끝까지 다시 설명하고, 재제출/재검토 담당과 남은 예외를 확인한 뒤 원본 REQ/AC의 구체적인 변경안으로 연결하는 것이다. 보완 제출·이력 보존이라는 두 선택만으로 상세 설계를 완료하지 않는다. 효율 개선은 아직 가설이며 실제 재질문·누락·보정 관찰로 평가한다.
