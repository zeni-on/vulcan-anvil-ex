# Part A. 내부 솔직 평가

## A1. 한 문장 결론

> Ex의 **방향(거버넌스 프레임워크)은 정확하고, 산출물 설계의 깊이는 동종 오픈소스 중 최상위권**이다.
> 그러나 **(1) 핵심 가치인 "규칙 준수"가 아직 소프트(마크다운) 강제에 크게 의존하고, (2) 그 가치가 README/공개 문서에서 충분히 선명하게 표현되지 않으며, (3) 타겟(감리/SI/규제 산업)이 글로벌 오픈소스 시장과 어긋나 있어 채택 동력이 약하다.**

방향은 맞다. 문제는 "효과적인가"가 아니라 "**누가, 어떻게 이걸 알고, 신뢰하고, 끝까지 따르게 만들 것인가**"이다.

## A2. 이 프레임워크가 실제로 무엇인지

겉보기에는 "AI 코딩 프레임워크"지만, 코드 생성 속도를 겨냥하지 않는다. 실제 정체성은 **AI가 만든 결과를 요구사항·설계·테스트·증적·승인 흐름으로 회수하는 거버넌스/추적성 운영 체계**다. 이 정체성은 자체 투자 문서에 이미 정확히 적혀 있다.

객관적 규모 (v0.4.6 기준, 2026-06 측정):

| 항목 | 규모 |
| --- | --- |
| `vulcan.py` | 약 15,170줄, 38개 서브명령 |
| Core 규칙 문서 | 26개 (`docs/core/`) |
| 산출물 템플릿 | 26개 |
| Runner adapter | 3개 (Codex/GPT, Claude, Gemini/Antigravity) |
| Persona | 16개 표준 작업 모드 |
| 개발 활동 | 최근 5일간 30+ 커밋 (매우 활발) |

이건 "주말 프로젝트" 규모가 아니다. 산출물 체계(기능명세서·프로그램명세서·API정의서·DB명세서·DBML ERD·보안가이드·단어사전·요구사항추적표)와 Gate별 검증 CLI(`check-trace`, `check-architecture`, `check-contract`, `drift-report`, `prepare-transition`)의 조합은 **상용 ALM 도구의 일부 기능을 LLM 워크플로우에 맞게 재해석한 수준**에 도달해 있다.

## A2.1. 실증 샘플 2건 — 같은 프레임워크, 다른 운영 강도

이 평가의 가장 강한 근거는 **실제로 end-to-end 완료된 두 샘플 프로젝트**다. 둘 다 단일 TODO 앱을 Phase 0~Gate 5까지 끝냈지만, profile에 따라 비용이 완전히 달랐다.

| 축 | PoC / Antigravity (`sample-ex-poc-agy-0609-1`) | Audit / Codex (`sample-ex-codex-0608-1`) |
| --- | --- | --- |
| Profile | `poc` | `audit` |
| Runner | Antigravity/Agy (native `Workspace: branch`) | Codex |
| 총 소요 | **약 11분 45초** (전 Gate 완료) | **약 1시간 50분** (전 Gate 완료) |
| 산출물 | PoC 3문서 세트 + 릴리즈 승인서 (4문서, 259줄) | 정식 산출물 23개 |
| Run 문서 | 1개 | 9개 |
| 코드 | 7파일, 1,412줄 | 전체 앱 |
| Gate 결과 | 7개 Gate 전부 done | 7개 Gate 전부 done |

**이 한 표가 자체 투자 문서가 주장한 "Profile별 무게 조절"이 실제로 작동함을 증명한다.** 같은 "전 Gate 완료"를 PoC는 ~12분, Audit은 ~1시간 50분에 해냈다 — 약 9배 차이. PoC가 "낮은 품질 모드가 아니라 문서 깊이가 낮은 모드"라는 원칙이 수치로 확인된다.

PoC profile은 무거운 audit 산출물 대신 **별도 3문서 세트**(`POC_REQUIREMENTS` / `POC_SYSTEM_DESIGN` / `POC_TEST_REPORT`)를 쓴다. 이는 로드맵이 "검증 대상"으로 올려둔 PoC 템플릿 세트 전략이 이미 작동 단계에 들어섰다는 뜻이다.

PoC 샘플의 Gate별 분해(회고 문서 기준)도 주목할 만하다:

| Gate | 소요 | 비고 |
| --- | ---: | --- |
| Phase 0 | 1분 2초 | PoC 목표·가설(HYP-001/002)·요구사항 |
| Gate 1 | 9초 | 요구사항 추적 확인 |
| Gate 2 | 10초 | 시스템 설계 + 정합성 검사 |
| Gate 3 | 8초 | 테스트 계획 |
| **Impl** | **4분 27초** | subagent(`todo_builder`) 격리 실행, npm install + 8파일 + self-check smoke |
| Gate 4 | 33초 | smoke 로그 수집 + 결과서 갱신 |
| Gate 5 | 45초 | 릴리즈 승인서 + release-pr dry-run |

문서 Gate(P0~G3)는 초 단위로 기계적으로 전환됐고, 시간의 대부분은 실제 코드를 짠 Impl에 쏠렸다. **즉 프레임워크 오버헤드 자체는 PoC에서 충분히 얇다.**

### 증적 규율은 PoC에서도 지켜졌다

PoC라고 증거를 느슨하게 적지 않았다. `POC_TEST_REPORT`는 실제 명령(`node test/db_smoke.test.js`), 실제 로그 경로(`test/logs/db_smoke.log`), 그리고 **과장 없는 판정**("Smoke Pass" — `Pass`로 부풀리지 않음)을 남겼다. 설계↔코드 계약 일치(스키마·REST·DTO)도 회고에서 100% 확인됐다. 이건 Ex의 핵심 가치(테스트 계획 vs 실행 증적 분리, 계약 검증)가 가장 가벼운 profile에서도 살아남았다는 증거다.

## A3. 가장 중요한 실증 발견 — 강제력이 약하다

**이 평가에서 가장 솔직하게 적어야 할 부분이다.** 프레임워크의 가치는 전적으로 에이전트가 규칙을 *따르는가*에 달려 있다. 그런데 **Ex를 실제 프로젝트에 적용한 런타임 세션**(`sample-anvil-ex-claude-1` 등 테스트 프로젝트를 Claude 런타임으로 진행한 세션)에서, 에이전트가 소프트 규칙을 반복적으로 어겼다. 이건 합성 테스트가 아니라 프레임워크를 만든 사람이 직접 적용하며 관찰한 실사용 증거다.

관찰된 위반 사례:

| 관찰 | 어긴 규칙 | 함의 |
| --- | --- | --- |
| 표준 P0 템플릿(`DOC-CORE-P0-001`)을 비워둔 채 `DIS-001_project-overview` 같은 비표준 ID 파일을 임의 생성 | ID 체계, "임의 파일 생성 금지" | ID 체계와 산출물 규약을 LLM이 무시 |
| `check-trace` 실행 없이 `session --status done`으로 Phase 0 완료 처리 | "check-trace 통과 전 Gate 전환 금지" | 핵심 안전망(Gate 게이팅)을 건너뜀 |
| RUN 문서(`run-new`) 없이 작업 시작 | "모든 의미 있는 작업은 Run으로 기록" | 추적성의 출발점 자체가 누락 |

**근본 진단**: `vulcan.py`가 일부 하드 게이트(`check-trace`, `check-architecture`, `run-preflight`)를 제공하지만, **이 명령을 *호출할지 말지*는 여전히 LLM이 선택한다.** 오케스트레이션 규율의 대부분은 마크다운 규칙(`CLAUDE.md`, `AGENTS.md`, persona 파일)에 적혀 있고, 그 준수는 모델의 자발성에 의존한다. 그리고 그 자발성은 — 프레임워크를 가장 잘 아는 사람이 운전해도 — 불안정했다.

이 발견은 부끄러운 곁가지가 아니라 **프레임워크의 작동 여부에 대한 중심 실증**이다. 그리고 이건 Ex만의 문제가 아니다. 모든 마크다운/프롬프트 기반 SDD 프레임워크(BMAD 포함)가 공유하는 구조적 한계다. 차이를 만들 수 있는 건 **얼마나 많은 규칙을 소프트에서 하드(거부 가능한 CLI 게이트)로 옮기느냐**이다. Ex는 이 방향으로 가장 멀리 가 있는 편이지만, 아직 "에이전트가 명령을 안 부르면 그만"인 경로가 많다.

**균형 잡힌 반대 증거**: A2.1의 PoC/Antigravity 샘플에서는 정반대였다. 그 세션의 회고는 "요구사항·설계서의 TBD가 완전히 해소되기 전에는 Impl로 넘어갈 수 없게 차단하는 가드레일 덕분에 설계 오염을 사전 차단했다"고 적었고, 에이전트가 `run-preflight`/`run-check`/`status --check`를 실제로 호출하며 진행했다. **즉 강제력의 실효성은 '프레임워크가 약하다'가 아니라 '에이전트가 check를 호출하는가'에 달려 있다.** 같은 프레임워크가 한 세션(claude-1)에서는 우회당하고 다른 세션(agy PoC)에서는 잘 작동했다. 이 변동성 자체가 핵심 문제다 — 신뢰성이 운(또는 runtime/프롬프트 품질)에 좌우되어선 안 된다. 해법은 명확하다: **check 호출 여부를 LLM 선택에서 떼어내 시스템이 강제하면, 좋은 세션의 결과가 모든 세션의 기본값이 된다.**

**개선 레버 (우선순위 순):**
1. **session 전환을 check 통과에 종속**: `session --status done`이 내부적으로 `prepare-transition`/`check-trace`를 자동 실행하고 실패 시 거부하도록. (LLM이 별도 호출을 빼먹어도 시스템이 막는다.)
2. **빈 표준 템플릿 잔존 시 Gate 완료 거부**: 이미 일부 구현됨. 전 Gate로 확대.
3. **작업 시작 시 Run 부재 감지**: 산출물이 수정됐는데 연결된 Run이 없으면 경고/거부.
4. **Agent-aware output checker** (로드맵 Later 항목): 비표준 ID, TBD, 얇은 delegation record를 가볍게 자동 검사 — **이걸 Later가 아니라 Now로 올려야 한다.** 이번 세션 증거가 그 근거다.

## A4. 타겟팅 — 분명하지만, 시장과 어긋나 있다

자체 투자 문서는 타겟을 정확히 안다: 감리·고객 검수·보안 검토·인수인계가 필요한 **장기 SI/규제 산업 프로젝트**. 이건 방어 가능한 니치다. 일반 AI 코딩 도구는 기능명세서·DB명세서·KISA 보안가이드·요구사항추적표 같은 **제출·감리용 산출물**을 만들지 않는다. Ex는 만든다. 이게 진짜 해자(垓子)다.

**그러나 두 가지 어긋남이 있다.**

**(1) 타겟 시장과 배포 채널의 불일치.** 이 니치(한국 공공/SI/감리)는 GitHub 오픈소스로 발견되는 시장이 아니다. 그 시장의 의사결정자는 GitHub star를 보고 도구를 고르지 않는다. 반대로 GitHub에서 이 repo를 발견하는 글로벌 개발자에게는 "감리/인수인계 산출물"이 핵심 가치로 와닿지 않는다. **가치를 가장 알아볼 사람과, 이 프로젝트가 노출되는 채널이 서로 다른 곳에 있다.**

**(2) 한국어 종속.** 거의 모든 핵심 문서·템플릿·persona가 한국어다. 이는 타겟(한국 SI)에는 정확하지만, 글로벌 오픈소스 채택은 사실상 차단한다. "글로벌 오픈소스로서의 성공"과 "한국 규제 산업용 도구로서의 성공"은 다른 전략이며, 현재는 둘 사이에 끼어 있다.

**판단 필요**: Ex는 (a) 한국 SI/감리 시장을 정조준한 한국어 전문 도구로 갈 것인가, (b) 글로벌 SDD 거버넌스 프레임워크로 영어화·일반화할 것인가. 둘은 양립하기 어렵고, 지금은 결정되지 않은 채 양쪽 비용을 모두 치르고 있다.

## A5. 경쟁 프레임워크 대비 — "초라하지 않다"

> 출처 주의: 아래 경쟁 도구 수치는 2026-06 웹 검색 기준이며, 빠르게 변한다. 카테고리·접근 수준의 비교는 신뢰할 수 있으나 구체 수치는 변동성이 크다.

먼저 **경쟁 상대를 올바로 잡아야 한다.** Ex의 경쟁자는 Cursor·Copilot·Devin(IDE 어시스턴트/자율 SWE 에이전트)이 아니라 **spec-driven / agentic-process 프레임워크**다.

| 프레임워크 | 형태 | 접근 | 강점 | Ex 대비 |
| --- | --- | --- | --- | --- |
| **GitHub Spec Kit** | 오픈소스 CLI (MIT) | spec → plan → tasks | 에이전트 무관, 72k+ star, 압도적 인지도 | Ex가 추적성·감리 산출물·승인 게이트에서 훨씬 깊음. 인지도·커뮤니티는 비교 불가하게 열세 |
| **AWS Kiro** | 상용 Agentic IDE (Code OSS 기반) | requirements → design → tasks → impl | IDE 네이티브, AWS 백킹, 3단계 강제 | Ex는 IDE가 아니라 runtime-agnostic. Kiro는 단일 IDE 종속 |
| **BMAD-METHOD** | 오픈소스 | 19+ persona 에이전트(PM/Architect/SM/Dev/QA), 50+ workflow, Claude Code 네이티브 hook | **Ex와 가장 유사**. persona+계획게이트+마크다운. 큰 커뮤니티 | Ex가 추적성 매트릭스·감리 산출물·변경관리(FIND/CR/ISSUE)·증적 분리에서 더 정밀. BMAD가 채택·생태계·다중 IDE 통합에서 압도 |

**핵심 통찰**: SDD(Spec-Driven Development)는 2025~2026에 사실상 업계 표준이 됐고, "spec → design → tasks → implementation"은 이제 흔하다. **거기까지는 Ex가 차별점이 없다.** Ex의 차별점은 그 *다음*에 있다:

- **요구사항추적표(traceability matrix)를 ID 원장으로 운영** — 대부분의 SDD 도구는 spec을 코드 생성 입력으로 쓰는 데 집중하고, 요구사항↔설계↔테스트↔증적의 영속적 연결 원장을 *1급 산출물로 전면에 내세우는* 도구는 드물다.
- **테스트 *계획*(Gate 3)과 실제 *실행 증적*(Gate 4)을 구조적으로 분리** — `Planned`를 `Pass`로 덮어쓰지 못하게 막는다. 이건 감리 관점에서 매우 드문 엄격성이다.
- **변경관리(FIND/CR/ISSUE/DEBT)를 정식 분류로 운영** — 경쟁 도구는 "버그 고쳐"로 끝내는 것을 Ex는 범위 내 결함(FIND) vs 베이스라인 변경(CR)으로 나눠 Gate 재진입을 강제한다.
- **설계-코드 drift를 자동 덮어쓰기가 아니라 보고서로 분리** (`drift-report`) — "구현이 설계를 지배하는" 문제를 명시적으로 방어. 이건 성숙한 거버넌스 사고다.
- **다중 runner를 하나의 Core 계약으로 회수** — Codex/Claude/Gemini 결과를 동일한 Run·산출물 계약으로 통합. BMAD가 Claude Code에 네이티브로 묶이는 것과 대조적으로, Ex는 runtime-agnostic을 의도적으로 유지.

**결론**: 기능 깊이와 거버넌스 정밀도로는 초라하지 않다. 오히려 감리/추적성 축에서는 동종 오픈소스 중 가장 깊은 편이다. **초라한 것은 인지도·커뮤니티·온보딩·접근성이다.**

## A6. 그 장점이 잘 표현되고 있는가 — 아니다 (이게 핵심 문제)

사용자가 던진 "장점이 잘 표현되고 있는지" 질문에 대한 솔직한 답: **표현이 가치를 따라가지 못한다.**

README의 문제:

1. **차별점이 묻혀 있다.** README는 "AI 협업 개발 운영 프레임워크"로 시작하는데, 이건 BMAD·Spec Kit·Kiro가 모두 하는 말이다. **Ex만의 한 줄("테스트 계획과 실행 증적을 분리하고, 요구사항↔증적을 추적표 원장으로 묶어 감리 가능한 산출물을 남긴다")이 첫 화면에 없다.** 진짜 해자가 24번째 줄, 155번째 줄에 흩어져 있다.

2. **내부 어휘가 진입을 막는다.** `delegation_records.mode: agy-branch-agent`, `workflow.integration_branch`, `BW-000 implementation-scaffold`, `run-preflight` 같은 용어가 README 본문에 등장한다. 이건 *이미 쓰는 사람*을 위한 운영 노트지, *처음 보는 사람*을 위한 소개가 아니다. README가 reference manual처럼 자라 있다.

3. **"무엇을 얻는지"보다 "어떻게 작동하는지"가 많다.** 38개 CLI, 3개 adapter, watchdog 타임아웃 JSON이 앞에 나오는데, "이걸 쓰면 감리 제출용 추적 가능한 산출물 묶음이 나온다"는 결과 가치는 약하게 표현된다.

4. **증거가 있는데도 안 보여준다 (가장 아까운 부분).** 이건 단순히 "증거가 없다"가 아니다. **증거는 이미 샘플 프로젝트에 존재한다.** `sample-ex-poc-agy-0609-1`의 회고 문서에는 Gate별 소요 시간, subagent duration(125초), 설계↔코드 100% 계약 일치, smoke 로그 바인딩까지 정량 기록이 있다(A2.1 참조). 그런데 이 구체적 성공 사례가 README/Dashboard 데모로 끌어올려지지 않아, 처음 보는 사람은 "11분 만에 PoC가 추적 가능한 산출물과 함께 끝났다"는 가장 설득력 있는 사실을 알 수 없다. 경쟁 도구들은 "3~10배 first-pass 성공률" 같은 수치를 *전면에* 내세운다. Ex는 더 정직한 자체 측정값을 *갖고도 숨기고* 있다.

## A7. 사용자를 위해 더 필요한 것

자체 투자 문서는 "더 가볍고 자동으로"라는 *내부 엔지니어링* 방향을 잘 잡았다. 여기서는 **사용자 채택 관점**에서 빠진 것을 보탠다.

| 격차 | 현재 | 필요 |
| --- | --- | --- |
| **완성 샘플의 가시성** | `docs/examples/`에 샘플이 있으나 README에서 "완성된 모습"을 보여주지 않음 | 끝까지 진행된 샘플 1개의 산출물 묶음 + 추적표 + Gate 진행 스크린샷을 README/Dashboard 데모로 전면 노출 |

| **영어/국제화 결정** | 한국어 종속 | A4의 전략 결정 후, 택한 방향에 맞게 정리 |

# Part B. 공개 요약판

> 이 섹션은 외부에 보여줄 수 있는 톤으로 작성한다. 솔직하되 강점·포지셔닝·로드맵 중심.

## Vulcan-Anvil Ex는 무엇인가

Vulcan-Anvil Ex는 **AI 에이전트가 만든 결과를 감리 가능한 프로젝트 산출물로 바꾸는 거버넌스 프레임워크**입니다. 코드를 더 빨리 만드는 도구가 아니라, AI가 빠르게 만든 코드를 **요구사항 → 설계 → 테스트 → 증적 → 승인**의 추적 가능한 흐름으로 묶어주는 작업대입니다.

## 어디에 강한가

Spec-Driven Development는 이제 흔합니다(GitHub Spec Kit, AWS Kiro, BMAD-METHOD). "spec → design → tasks → 구현"까지는 많은 도구가 합니다. Ex는 **그다음**에 차별점이 있습니다.

- **요구사항추적표 원장**: 요구사항↔설계↔테스트↔증적을 ID로 영속 연결합니다.
- **테스트 계획 vs 실행 증적 분리**: `Planned`를 `Pass`로 덮어쓰지 못합니다. 감리 관점의 엄격성입니다.
- **정식 변경관리(FIND/CR/ISSUE)**: 단순 버그 수정과 베이스라인 변경을 구분하고 Gate 재진입을 강제합니다.
- **설계-코드 drift 분리**(`drift-report`): 구현이 설계를 임의로 덮어쓰지 못하게 막습니다.
- **Runtime-agnostic**: Codex·Claude·Gemini/Antigravity 결과를 하나의 Core 계약으로 회수합니다. 특정 IDE/런타임에 종속되지 않습니다. 실제로 Antigravity의 native `Workspace: branch`로 subagent를 격리 실행하고, 검증 후에만 통합하는 방식이 샘플에서 동작했습니다.

## 누구에게 맞는가

| 잘 맞음 | 과할 수 있음 |
| --- | --- |
| 감리·고객 검수·인수인계가 필요한 프로젝트 | 하루짜리 throwaway 프로토타입 |
| 장기 유지보수되는 SI/솔루션 | 추적이 필요 없는 개인 실험 |
| PM/개발/QA/리뷰어 관점이 나뉘는 팀 | 이미 강한 ALM/감리 도구가 자리잡은 조직 |
| 여러 AI runtime을 섞어 쓰는 환경 | 즉시 동작 데모가 결과 품질보다 중요한 작업 |

가벼운 검증이 필요하면 `--profile poc`, 감리/인수인계가 필요하면 `--profile audit`로 운영 강도를 조절합니다. 이건 말뿐이 아닙니다 — 실제 샘플에서 같은 TODO 앱을 **PoC profile은 약 12분**(3문서 + 1 Run + 1,412줄 코드, 전 Gate 완료), **Audit profile은 약 1시간 50분**(정식 산출물 23개 + 9 Run, 전 Gate 완료)에 끝냈습니다. PoC에서도 테스트 로그·계약 일치 검증 같은 증적 규율은 유지됩니다.

## 현재 상태와 솔직한 한계

Ex는 **실험 단계(v0.4.x)**입니다. 안정 제품이 아니며, 다음을 인정합니다.

- **규칙 준수는 부분적으로 소프트 강제**입니다. `vulcan.py`가 `check-trace`, `check-architecture` 등 하드 게이트를 제공하지만, 전 과정이 프로그램으로 강제되지는 않습니다. 실제 샘플에서는 가드레일이 잘 작동해 TBD 미해소 시 구현 진입을 차단한 사례가 있는 반면, 다른 세션에서는 에이전트가 일부 check를 건너뛴 사례도 있었습니다. 이는 모든 마크다운 기반 SDD 프레임워크의 공통 과제이며, Ex는 이를 점점 더 하드 게이트로 옮기는 방향입니다.
- **커뮤니티·생태계는 초기 단계**입니다. BMAD·Spec Kit 같은 도구의 인지도에는 못 미칩니다.
- **개인이 운영하는 오픈소스**이며 특정 회사·고객의 공식 산출물이 아닙니다.

## 로드맵 방향

다음 투자는 "더 많은 규칙"이 아니라 **"더 가볍고, 더 자동으로 검증되게"**입니다.

1. 강제력의 하드화 — 핵심 규칙을 거부 가능한 CLI 게이트로
2. Profile별 무게 조절 — PoC를 진짜 5~10분 fast-track으로
3. 추적성 그래프 기반 자동 추천 — 사람이 ID를 긁어오지 않게
4. QA 안정화 — 테스트 실행자와 수정자 역할 분리
5. Dashboard — 많은 정보가 아니라 판단 가능한 신호

자세한 내용은 [`ROADMAP.md`](../ROADMAP.md)와 [`EX-DIRECTION-INVESTMENT-REVIEW.md`](EX-DIRECTION-INVESTMENT-REVIEW.md)를 참고하세요.
