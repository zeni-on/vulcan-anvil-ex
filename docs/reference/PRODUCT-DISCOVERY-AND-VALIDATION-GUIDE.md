# Product Discovery And Validation Guide

- 상태: 작성 운영 연결 / 실제 업무 흐름 검증 전
- 작성일: 2026-09-10
- 업데이트: 2026-09-12
- 적용 검토 범위: Product의 기획·설계 구간과 이후 기능 확장 시 영향 범위 재검토
- 연습: [요청 보드 파일럿](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md)

대화 파일럿 이후 유용한 작성 경로를 [Product Document Writing 0절](../core/PRODUCT_DOCUMENT_WRITING.md#0-업무에서-요구로-연결한다)과 선택 업무 흐름 템플릿에 연결했다. 이 문서는 기법·출처 설명이며 운영 규칙의 원본은 Core다. 필수 산출물/Gate를 늘리거나 기존 프로젝트의 승인 문서를 자동 변경하지 않는다.

상위 운영 방향은 [Product 3구간 설계](PRODUCT-ITERATIVE-PROCESS-DESIGN.md)를 따른다. 제품 정의와 설계는 같은 구간에서 반복하며, 아래 활동별 문서 역할을 각각의 Gate로 만들지 않는다. 3구간은 표식 있는 실험 세션에서만 사용하고, 표식 없는 프로젝트의 기존 Gate 순서는 유지한다. 작성 가이드 배포와 새 프로세스의 일반 활성화는 별개다.

## 1. 목적

개별 요구사항을 구현했지만 실제 업무는 끝낼 수 없는 문제를 줄인다. 상세 API/DB/UI 설계에 들어가기 전에 **누가, 어떤 상황에서, 무엇을 끝내려 하며, 예외가 생기면 어떻게 이어가는지**를 사용자와 확인한다.

에이전트는 자료 수집, 흐름 초안, 모순 탐색, 변경 영향 정리를 담당한다. 업무 의미와 우선순위는 권한 있는 사용자·이해관계자가 판단한다. 답을 대신 만들어 문서를 완성하는 것이 목표가 아니다.

## 2. 참고 기반

아래는 서로 다른 수준의 표준·지식체계·기법이다. 한 방법론으로 동일시하거나, 모두 도입해야 한다고 해석하지 않는다. 이 문서의 순서와 Gate 매핑은 Ex에 맞춘 제안이지 각 출처가 의무화한 절차가 아니다.

| 기반 | 확인한 개념 | Ex에서 활용할 부분 | 적용하지 않는 해석 |
| --- | --- | --- | --- |
| [IIBA Business Analysis Standard / BABOK 안내](https://www.iiba.org/knowledgehub/the-business-analysis-standard/) | 요구 도출·확인, 현재/미래 상태 분석, 요구 검증·타당성 확인, 변경 관리 | 업무 분석 활동의 전체 틀 | 모든 기법·문서를 순서대로 수행하는 고정 프로세스 |
| [IREB CPRE Requirements Elicitation](https://cpre.ireb.org/en/concept/requirements-elicitation) | 이해관계자·문서·시스템에서 요구를 찾고, 상황에 맞는 기법으로 충돌과 오해를 해소 | 출처 확인, 필요한 질문 선택, 해석 차이 확인 | 에이전트끼리 합의하면 실제 사용자의 요구도 확인됐다는 주장 |
| [ISO/IEC/IEEE 29148:2018 공개 개요](https://www.iso.org/standard/72089.html) | 생명주기 전반의 요구공학 프로세스와 정보 항목 | 요구의 근거·내용 품질·생명주기를 점검하는 참조 기준 | Ex 검사 통과를 ISO 준수 인증으로 표현 |
| [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/About-BPMN) | 업무 프로세스와 참여자 간 협업을 표현하는 표기 | 역할 간 인계·분기가 복잡할 때 선택적으로 모델링 | 모든 작은 기능에 BPMN 도구·실행 엔진을 의무화 |
| [Cucumber Example Mapping](https://cucumber.io/docs/bdd/example-mapping/) | 이야기, 규칙, 구체적 예시, 미해결 질문을 구분하는 대화 | 한 시나리오의 이해를 예시로 맞추기 | Gherkin 파일 작성이나 Cucumber 설치를 선행 조건으로 요구 |

2026-09-10에 공개 안내를 확인했다. 유료 표준 전문·교재 전체를 검토한 것은 아니며 원문을 템플릿에 전재하지 않는다. 특히 ISO 준수가 필요한 프로젝트는 해당 판본의 정식 원문과 고객 기준을 별도로 검토해야 한다. 단순 Mermaid 흐름도를 BPMN 준수 모델이라고 부르지 않는다.

## 3. 대화 운영

### 3.1 준비와 책임

| 담당 | 할 일 | 대신하면 안 되는 일 |
| --- | --- | --- |
| 사용자·업무 결정자 | 문제, 업무 규칙, 우선순위, 수용할 결과와 제외 범위를 판단 | 템플릿·ID·모든 링크를 직접 관리할 필요는 없음 |
| 총괄 에이전트 | 기존 근거 읽기, 흐름 초안, 질문과 대안, 답의 영향 분석, 원본 현행화 후보 | 사용자 대신 중요한 권한·상태·업무 정책 확정 |
| 필요 시 설계·품질 보조 | 기술적 실현 가능성, 빠진 예외, 관측 가능한 결과 검토 | 역할 수를 채우기 위한 불필요한 agent 생성, 업무 합의 대행 |
| 프로그램 | 원본에서 ID 목록·연결·누락·충돌 수집 | 요구가 실제 업무에 맞는지 또는 사용자가 동의했는지 추정 |

처음에는 목표/범위와 선택한 흐름의 원본, 적용 공통 정책만 읽는다. 프로젝트 전체 문서와 과거 Run을 매번 입력하지 않는다. 기존 자료의 서술은 출처 있는 내용이지만 사용자 합의가 확인되지 않았다면 승인 사실과 구분한다.

### 3.2 한 흐름을 함께 확인하는 순서

1. **문제와 경계 확인**: 지금 누가 어떤 일을 놓치고 있는가? 제품이 해결할 부분과 사람·외부 시스템에 남길 부분은 무엇인가? 사용자 외 운영자·영향받는 이해관계자도 필요한 범위에서 확인한다.
2. **대표 상황 재생**: 시작 사건, 참여자, 행동과 인계, 정상 종료를 구체적 한 건으로 설명한다. 화면·테이블·API부터 결정하지 않는다.
3. **결과가 달라지는 분기 탐색**: 반려, 취소, 재시도, 중복, 권한 변경, 외부 실패 등 해당 업무에서 중요한 경우를 선택한다. 보안·보존·접근성·운영 제약도 영향이 있으면 질문한다. 모든 경우를 매번 기계적으로 묻지 않는다.
4. **규칙·예시·질문 분리**: 답이 있는 규칙에는 구체적인 입력/행동/관측 결과를 붙이고, 답이 없는 것은 질문으로 남긴다. 기술적으로 편리한 선택을 업무 기본값으로 확정하지 않는다.
5. **되짚고 요구로 연결**: 사용자 답을 짧게 재진술하고 대표·예외 예시가 의도와 맞는지 확인한다. 그다음 기존 SCN/REQ/AC 원본에 반영할 후보와 영향 범위를 제시한다. 새 기능이 아니면 기존 ID를 유지한다.

질문은 업무 결과를 크게 바꾸는 것부터 한두 개씩 다룬다. 선택지를 제시할 때는 영향과 추천 이유를 설명하되 자유로운 답변을 허용하고, 미리 선택된 값을 사용자 답으로 간주하지 않는다. 이미 답한 질문은 해당 근거를 재사용하며 변경 징후가 있을 때만 다시 묻는다.

자료·담당자 부재로 답이 없으면 이유와 다음 확인 담당/시점을 남긴다. 영향받는 계약의 확정은 보류하되 독립적으로 진행 가능한 승인 범위까지 일괄 중단하지 않는다. 다만 권한·금전·개인정보·돌이키기 어려운 데이터 의미를 바꾸는 가정을 조용히 구현하지 않는다.

### 3.3 대화가 남기는 내용

별도 질문 원장이나 Run을 매번 만들지 않고 기존 업무 상세의 관련 절에 다음을 짧게 구분한다.

- 확인한 문제·목표와 근거: 사용자 설명, 현행 절차, 문서 등 출처.
- 대표 흐름: 누가 시작하고 어디서 종료하는지, 경계 밖 책임.
- 규칙과 예시: 합의한 동작과 관측 가능한 결과. 아직 실행한 테스트는 아님.
- 열린 질문: 미정 내용, 영향을 받는 범위, 확인할 사람/시점.
- 결정과 변경 영향: 합의 근거, 바뀌는 기존 원본, 별도 승인 또는 제외가 필요한 범위.

이는 작성 관점이지 새 필수 YAML 필드나 ID 체계가 아니다. 대화 전문을 문서에 누적하지 않는다. 이 파일럿의 사례별 기록은 [연습 문서](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md) 한 곳에 둔다.

## 4. 기획·설계 안의 활동과 다음 구간

| 시점 | 확인할 내용 | 다음 단계에 전달할 것 |
| --- | --- | --- |
| 기획·설계: 업무 정의 | 문제·가치·이해관계자·업무/시스템 경계·큰 가정 | 제품 목표와 업무 범위, 대표 상황 후보, 중요한 미정 사항 |
| 기획·설계: 흐름·요구 | 액터 책임, 정상/대안 흐름, 용어·상태·규칙, REQ/AC와 목표의 관계 | 업무 흐름과 예시, 관측 가능한 AC, 미해결 영향 |
| 기획·설계: 기술·검증 설계 | API/DB/UI/보안·운영 설계와 시험 계획이 업무 흐름·공통 제약을 지원하는지 | 상세 계약, 시험 입력/행동/기대값, 환경과 방법. 실행 Pass는 아님 |
| 구현 | 합의한 범위를 코드와 담당 테스트로 만들 수 있는지 | 통합 후보, 실제 self-check 결과, 변경/질문 후보 |
| 인수 검증 | 통합된 실제 제품에서 업무가 끝까지 되는지 | 실제 관측·증적, 실패/환경 차단, 해당 범위의 수용 판단 |

기획·설계의 세 행은 활동 관점이지 세 개의 하위 Gate가 아니다. 질문이나 기술 제약을 발견하면 같은 구간에서 필요한 원본으로 돌아간다. 구현 범위의 허가와 결과 수용, 필요한 변경·배포 승인은 구분하며 답 하나를 받은 것을 전체 구현/인수 승인으로 기록하지 않는다. 처음에 모든 미래 기능을 분석하고 동결하지 않는다. 새 모델 구현 전에는 기존 Gate 운영 기준이 계속 적용된다.

업무상 확인과 기계적 검사는 구분한다. IIBA는 요구의 품질을 확인하는 verification과 필요/가치에 맞는지 확인하는 validation을 구분한다. 따라서 ID·링크가 정합해도 업무 타당성이 입증된 것은 아니다. [IIBA 용어집](https://www.iiba.org/career-resources/a-business-analysis-professionals-foundation-for-success/babok/glossary/)

## 5. 문서와 기능 확장

현재 작성 경로는 [Product Document Writing](../core/PRODUCT_DOCUMENT_WRITING.md)을 따른다. 6종 진입점을 다시 거대 문서로 만들거나 각 대화 단계마다 파일을 하나씩 만들지 않는다.

| 정보 | 현재 작성 경로 |
| --- | --- |
| 목표·범위·핵심 사용자/시나리오 | Product Brief를 진입점으로 유지 |
| 업무 경계·액터 책임·흐름·규칙 | 규모가 커지면 업무/기능별 원본으로 분리하고 Brief에서 링크 |
| REQ/AC | 이미 있는 `01-requirements` 원본. 업무 설명을 요구 행마다 복사하지 않음 |
| API/DB/UI/보안, 시험 정의·실행 | 기존 설계·시험·결과 원본에 연결. 기대값과 실제 결과는 분리 |
| 전체 AC 등 목록 | 원본에서 자동 수집하는 조회 기능으로 제공할 후속 과제. 수동 복제 원장을 만들지 않음 |

선택 [업무 흐름 템플릿](../templates/product/PRODUCT_BUSINESS_FLOW_TEMPLATE.md)은 기존 `docs/artifacts/01-requirements/<domain>-flow.md`를 사용한다. 작은 흐름은 기존 요구 상세에서 작성한다. Brief resolver/조회/Dashboard가 이미 사용하는 경로를 유지하고 `00-discovery` 자동 수집을 추가하지 않는다. [작성 예시](../../scripts/regression/fixtures/product-discovery-writing/README.md)에서 규칙·예시·질문과 REQ/AC 후보, Planned 시험의 연결을 확인할 수 있다. 예시의 후보를 실제 업무 승인으로 사용하지 않는다.

새 액터/권한, 상태 전이, 승인·반려·취소·재시도, 외부 책임, 데이터 의미/보존, 성공 기준을 바꾸면 영향을 받는 업무 흐름을 먼저 재확인한다. 단순 오탈자·표현·동작 변화 없는 스타일 수정 때문에 전체 업무 분석을 다시 하지 않는다. 실제 의미 영향이 불분명하면 그 지점만 확인한다.

변경 시 원본의 현재 명세를 현행화하고 변경 이유는 기존 결정/CR/Git 근거에 연결한다. 승인된 규칙과 충돌하면 [기존 변경 절차](../core/CHANGE_CONTROL_PROCESS.md)를 적용한다. 기능별 파일이 늘어나더라도 공통 규칙은 한 곳에 유지하고 적용 링크로 연결한다.

## 6. 적용과 확인 순서

아래 작성 연결 시점의 미정 기록 이후, 2026-09-12 [후속 샘플 합의와 로컬 검증](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md#9-로컬-실행-샘플의-후속-합의-2026-09-12)이 이루어졌다. 원격 CI는 다음 범위로 남긴다. 과거 후보 예시를 승인 문서로 바꾸지는 않는다.

1. **대화 파일럿**: 요청 보드의 의미 공백, 사용자 두 선택과 후속 질문을 기록했다. 권한·상태·보존 경계는 아직 미합의다.
2. **현재: 작성 운영 연결**. Core 0절과 선택 양식에서 업무 원본→REQ/AC→시험을 연결하고 후보/현재·입력/결과를 구분한다. 기존 Codex/Gemini bootstrap의 공통 작성 문서 경로를 그대로 사용한다. 실험 세션은 CLI Guide 4.1절, 표식 없는 세션은 기존 Gate를 따르며 adapter마다 방법론을 복제하지 않는다. init/upgrade는 선택 양식만 설치하고 작성된 원본은 보존한다.
3. **같은 샘플에서 업무 시험과 CI 연결**. [제품별 CI 설계](PRODUCT-CI-AND-QUALITY-LOOP.md)에 따라 합의한 예시를 실제 assertion으로 만들고 로컬/CI에서 실행한다. 실패·필수 시험 누락·환경 차단을 검증한 뒤 Product 기준 채택을 판단한다. workflow 파일이나 코드 정합성만으로 업무 검증 완료라고 하지 않는다.
4. **후속: 프로그램 기반 전체 목록**. 분리된 원본에서 AC/REQ 등 전체 조회를 제공하고 출처/중복/미수집 범위를 표시한다. 업무 판단을 자동 승인하는 기능은 넣지 않는다.

파일럿에서는 발견한 의미 공백, 사용자 결정으로 바뀐 조건, 놓친 예외와 재질문을 기록한다. 문서 분량·속도·비용 절감은 실측 전 성과로 주장하지 않는다. 완료 기준은 서류 수가 아니라 **사용자가 의도한 한 업무 흐름을 서로 같은 예시로 설명하고, 요구/AC 후보에 연결할 수 있는가**다. 이것도 실제 제품 QA 통과와는 별개다.

## 7. 작성 연결 검증 (2026-09-12)

- 이번 마무리 범위 2는 작성 운영 경로다. Core의 질문/원본 책임, 선택 업무 흐름 양식, 요구의 primary REQ 행과 AC 조건/행동, 기존 Codex/Gemini 라우팅을 연결했다. 새로운 필수 산출물·Gate·Run·CLI나 자동 업무 승인은 없다.
- [작성 회귀](../../scripts/regression/tests/test_product_discovery_writing.py) 10건을 포함한 Python 영향 시험은 102건 실행, 101건 통과/로컬 symlink 제약 1건 skip이었다. 후보 제외, 합성 채택 후 정의의 단일 원본, Planned 계획/실행 구분, 필수 원본 링크 누락·변경 차단, 실제 선택 템플릿 렌더/수집과 로컬 링크·앵커를 확인했다. 전체 Python suite를 다시 실행한 결과로 표현하지 않는다.
- Codex/Gemini init의 6종 원장 유지·선택 양식 설치와 upgrade의 작성된 원본 보존은 기존 작성 회귀로 확인했다. 초기화 smoke 12단계, 기존 Product/PoC/Audit fixture smoke 84단계도 통과했다.
- Dashboard 문서 API 시험 21건이 통과했다. `01-requirements`의 업무 흐름/요구 상세를 기존 요구사항 분류로 읽는 회귀를 추가했다. 화면/렌더러 코드는 변경하지 않았고 로컬 전체 build/E2E는 반복하지 않았다. 원격 PR CI는 별도 결과다.
- 새 문맥의 native contract-reviewer는 읽기 전용 검토에서 수정 필요 지적을 찾지 않았다. 선택 업무 양식 자체의 렌더/수집 시험이 빠졌다는 비차단 의견은 총괄이 테스트에 보완하고 위 최종 영향 시험으로 확인했다. 기존 pathlib deprecation warning은 남아 있다.
- 미정 권한·상태·보존 정책은 실제 사용자 합의로 채우지 않았다. 예시의 SCN/REQ/AC는 독립 합성 namespace이며 기존 프로젝트를 수정하지 않는다. 기계적 연결 성공은 업무 타당성/구현 허가/QA 성공을 입증하지 않는다. 다음은 업무 합의 후 실제 요청 보드 흐름 검증이며 일반 활성화와 PMTool 이행은 이번 범위가 아니다.
