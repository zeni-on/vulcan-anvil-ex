# Product Iterative Process Scenarios

- 상태: 2026-09-11 운영 시나리오·기대 행동 / runtime 시험 미수행
- 기준: [Product 3구간 설계](PRODUCT-ITERATIVE-PROCESS-DESIGN.md)

아래는 구현할 프로세스의 인수 기준이다. 행 번호는 설명용이며 새 프로젝트 SCN/AC/Run ID 체계가 아니다. 현재 CLI를 이 표의 새 구간으로 실행하거나 실제 프로젝트를 변경하지 않는다. 제품 기능의 테스트와 프레임워크 운영 시험을 구분한다.

## 1. 흐름별 기대 행동

| 사례 | 입력/전제와 진행 | 문서·권한 처리 | 기대 결과와 금지할 오인 |
| --- | --- | --- | --- |
| 신규 기능 | 가상 요청 보드의 문제·액터·흐름을 논의하고 요구/AC, 설계, 시험 방법을 구체화. 해당 범위 구현 허가 후 구현·검증 | 업무/요구·설계·시험 원본을 연결. 기획·설계 내부 이동에 별도 승인/Run을 만들지 않음 | 준비 검사만 통과해서 무허가 구현하지 않음. 인수 필수 결과와 수용 근거가 있어야 이번 범위 완료 |
| 설계 중 업무 질문 | 이력 저장 방식을 검토하다 보존 기간·권한이 미정임을 발견 | 같은 기획·설계에서 영향 질문. 독립적으로 허용된 설계 후보는 계속 작성 | Phase 0 회귀/전체 문서 재작성 없음. 영구 보존·전체 공개를 임의 기본값으로 정하지 않음 |
| 완료 제품에 기능 추가 | 요청 등록/검토가 완료된 제품에 댓글 기능을 제안 | 댓글과 적용 공통 권한만 영향 분석. 기존 구현·증적은 보존하고 새 범위의 준비/허가를 식별 | 기존 코드가 있다는 이유만으로 기획 금지하지 않음. 요청 기능 수용을 댓글 기능 수용으로 재사용하지 않음 |
| 인수 중 구현 결함 | 합의된 재제출 동작에서 이전 내용이 지워짐. 코드 결함으로 확인되고 해당 수정은 이미 위임 범위 안 | 실패와 당시 증적 보존. 구현 담당이 코드/테스트 수정, 품질 담당이 현재 소스 재검증 | 전체 요구·설계 재승인 없이 구현으로 반환. 테스트 기대값을 낮춰 Pass를 만들지 않음 |
| 인수 중 업무 변경 | 인수 과정에서 승인된 요청까지 보완할 수 있게 하자는 새 요청 발생 | 승인 후 불변 규칙과 충돌하는 변경 후보로 기획·설계의 영향 부분에 반환 | 단순 bug fix로 구현하지 않음. 새 의미/범위를 확인하고 허가를 얻음 |
| 환경 차단 | UI 시험의 브라우저/서버 준비 실패 | 환경 차단·미실행을 결과에 기록. 허용된 환경 복구만 수행 | Not Run을 Pass로 바꾸거나 UI를 자동 제외하지 않음. 인수 완료는 보류 |
| 문서 표현만 변경 | 기능/시험/공통 조건 변화 없이 링크나 오탈자 정리 | 내용 보존·링크와 실제 diff를 확인 | 제품 시험을 문서 변경 횟수만큼 반복하지 않음. 의미가 바뀌면 이 사례로 처리하지 않음 |
| 코드 통합 후 기준 변경 | worker 증적은 있으나 통합 중 공유 코드가 달라짐 | 테스트·의존성·환경·소스 기준을 비교하고 영향 재검증 | 같은 브랜치/worker 성공 요약만으로 증적 재사용하지 않음 |
| 위임받지 않은 결함 수정 | 품질 담당이 제품 결함을 발견했으나 수정 허가는 없음 | 결함/재현·영향·수정 후보를 총괄에게 반환 | QA 담당이 조용히 코드/승인된 설계를 고치지 않음. 허가 확보 후 수정·재시험 |
| 다음 기능의 병렬 기획 | 현재 기능을 구현하는 동안 독립적인 다음 기능의 기획 담당이 조사 | 다음 기능은 후보 원본에서 작업. 현재 승인 범위와 공통 상태는 총괄이 관리 | 여러 작업창을 이유로 미승인 구현·현재 계약 덮어쓰기·다중 active Wave를 허용하지 않음 |
| 검증 충족, 수용 대기 | 모든 필수 검증 결과가 있지만 사용자 수용 답변은 아직 없음 | 결과/잔여 위험을 인수 후보로 제시 | ready와 accepted 구분. 에이전트가 승인 플래그만 생성해 완료하지 않음 |
| 인수 후 배포 요청 없음 | 이번 변경은 수용됐지만 운영 배포·main merge 지시는 없음 | 수용 기준은 보존하고 배포 필요/허가는 별도 표시 | 인수를 이유로 자동 merge/push/배포하지 않음. 수용과 출시를 혼동하지 않음 |
| 완료 후 또 다른 수정 | 새 결함 또는 다음 범위가 들어옴 | 계약 변화가 없고 수정 범위 허가가 있으면 구현, 없으면 기획·설계에서 영향 확인 | 완료가 제품의 영구 종료가 아님. 과거 완료·미완료 의무를 삭제하지 않음 |

위 행은 설계 검토용이며 모든 항목이 실행 통과했다는 보고가 아니다. 후속 구현 시험에서는 각 전제의 실제 원본/소스/허가, 수행 행동, 관측 결과를 구분해서 기록한다.

## 2. 요청 보드 대화로 구체화한 한 사례

[기존 연습](PRODUCT-DISCOVERY-PILOT-REQUEST-BOARD.md)에서 사용자가 선택한 것은 다음 두 가지다.

- 기존 요청을 보완해 재제출한다.
- 반려 당시 내용과 사유를 모두 보존한다.

재제출·재검토 권한, 편집 중 상태, 보존 기간/조회 범위는 아직 합의하지 않았다. 아래는 3구간 프로세스에서 이 미정을 다루는 방식이다.

1. **기획·설계**: 위 두 선택을 현재 초안의 결정 후 변경 금지 규칙과 비교한다. 민수가 '장비 필요'를 '장비 2대 필요'로 보완하는 예시를 제시하고, 기존 내용과 사유가 사라지지 않는다는 AC 후보를 만든다.
2. **같은 기획·설계**: 권한·상태·보존 정책 중 이번 구현을 막는 부분만 사용자에게 확인한다. 원본·공통 조건·시험 계획과 범위가 명확해지면 구현 허가를 요청한다. 이 시점까지 실제 구현 허가는 받지 않았다.
3. **구현 허가 이후의 기대 행동**: 합의한 범위의 코드를 작성하고 담당 테스트를 수행한다. 예외나 새 요구가 나오면 영향 범위만 반환한다. 이 단계는 아직 수행하지 않았다.
4. **인수 검증의 기대 행동**: 통합 소스에서 반려→보완→재제출과 이력 보존·권한을 검증한다. 이전 내용이 지워지면 실패로 남기고 허용된 수정으로 반환한다. 확인한 실제 결과를 인수 책임자가 수용한 뒤 이번 변경을 완료한다. 아직 실제 결과/수용 근거는 없다.

세 구간은 사용자와 에이전트의 진행 단위이며, 네 번째 항목이나 재시험 횟수만큼 Gate가 늘어나는 것은 아니다. 명세/코드/증적 파일의 역할도 구간 수에 맞춰 합치지 않는다.

## 3. 후속 회귀 시험 항목

| 대상 | 고정할 관측 |
| --- | --- |
| 상태·승인 | planning→impl에는 현재 범위 허가 필요, impl→acceptance는 허용된 검증 실행으로 이동, acceptance→completed에는 필수 결과·수용 근거 필요 |
| 승인 범위 변경 | 대상 ID/공통 계약/기준 revision이 다른 새 기능에 과거 승인 재사용 불가. 표현만 바뀐 경우는 의미 영향 판단과 구분 |
| 완료 후 재진입 | 기존 소스·문서·완료/실패 증적 보존. 새 범위를 구별하고 과거 필수 미완료 의무를 조회 가능 |
| 부정 사례 | 무허가 구현, 기대값 변경으로 실패 은폐, 미실행 Pass, 환경 차단 자동 제외, 인수 후 무허가 배포 차단 |
| 읽기 전용 진단 | status/준비 조회가 상태·문서·승인·Git을 변경하지 않음. ready는 승인 아님 |
| Legacy Product | process model 표식이 없으면 기존 의미 유지. upgrade만으로 변환하지 않음 |
| 명시 이행 | dry-run과 실제 적용 전후 원본/상태/승인 기준 비교. 진행 중 worker·불명확 승인·호환되지 않는 도구가 있으면 먼저 정리 |
| 미지원 모델·Dashboard | 새 모델 읽기/쓰기의 명시 진단, 구버전 데이터 호환, 3구간/현재 범위/수용·배포 상태 표시 |
| 다른 profile | Audit/PoC의 기존 fixture·Gate/승인/QA 기대값 불변 |

현재의 문서 검토는 이 회귀 시험을 실행한 증적이 아니다. runtime 구현과 함께 합성 fixture에서 재현하고, 실제 프로젝트 이행은 보존 비교와 별도 허가 후 진행한다.
