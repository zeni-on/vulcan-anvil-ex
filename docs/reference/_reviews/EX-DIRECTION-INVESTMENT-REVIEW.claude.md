# Verdict

방향성은 일관되고 설득력 있다. "AI coding governance framework" 포지셔닝은 Codex/Claude/Cursor와의 직접 경쟁을 피하면서 audit/SI 시장의 실제 미충족 수요를 겨냥한다. 다만 (a) governance 가치를 **측정 가능한 형태로 입증할 방법**, (b) **PoC profile이 실제로 가벼워질 수 있다는 가정**, (c) **경쟁 도구가 governance 레이어를 흡수할 위험**에 대한 분석이 얇다. 계속 투자 결론은 유효하나, "투자 지속 여부를 판가름할 정량 신호"를 문서에 명시해야 6개월 뒤 같은 질문에 다시 답할 수 있다.

# Strengths

- **포지셔닝이 명확하다.** "accelerator가 아니라 governance" 한 줄 정의가 §2·§8에서 일관된다.
- **적용 조건과 부적합 조건을 모두 명시**(§3)했다. 만능 도구를 자처하지 않아 신뢰도가 높다.
- **위험 신호와 축소 신호를 분리**(§4 vs §7)해 retreat path를 사전에 설계한 점이 좋다.
- **Profile 분리**(§5.1)와 "PoC는 낮은 품질 모드가 아니다"라는 정의는 흔한 오해를 선제 차단한다.
- **QA worker는 수정하지 않는다**(§5.4) 원칙은 governance framework의 정체성과 정확히 일치한다.

# Risks

1. **Governance 가치의 ROI 부재.** "audit/인수인계에서 가치가 있다"는 주장은 맞지만, 사용자/고객이 그 가치를 **얼마에 사는지** 문서에 없다. governance는 사고가 나야 가치가 드러나는 보험형 자산이라, "투자 지속" 판단이 감으로 흐를 위험.
2. **경쟁 도구의 흡수 위험 미평가.** Cursor/Claude Code가 6~12개월 내 trace/evidence 레이어를 기본 탑재할 가능성이 있다. Ex가 "Core 규칙 + Run 계약 + Gate 승인"을 **adapter-agnostic 표준**으로 만들지 못하면, 단일 도구의 부속으로 함몰된다. §5에 이 방어 전략이 없다.
3. **PoC profile 가벼워짐 가정이 약하다.** §6.5는 "일반 AI coding tool에 가까운 속도"를 조건으로 거는데, §5.1~5.3 어디에도 PoC가 그 속도에 도달할 메커니즘이 구체화돼 있지 않다. governance 골격을 유지하면서 PoC를 가볍게 만드는 것은 구조적 모순일 수 있다.
4. **Trace graph 자동 추천(§5.3)의 정확도 risk.** 추천이 틀리면 Orchestrator 보정량이 §4-1·4-6의 위험을 오히려 키운다. 추천 정확도 측정 지표가 §5.5 측정 항목에 빠져 있다.
5. **사용자(=최종 판단자) 한 명에 대한 의존.** §3은 "사용자가 최종 판단자"를 효과 조건으로 두는데, 이는 곧 **사용자 부하가 병목**이라는 뜻이다. governance 부담을 다인 팀에 분산하는 시나리오가 빠져 있다.
6. **"더 가볍고 자동으로"와 "설명 가능성 유지"의 충돌.** 자동 추천·자동 검증을 늘리면 evidence 출처가 불투명해진다. audit profile에서 자동화 산출물의 검증 가능성 기준이 없다.
7. **샘플 프로젝트 수가 작을 위험.** §6 기준이 "샘플 프로젝트"에 묶여 있다. 표본이 1~2개면 잘못된 일반화가 나온다.

# Suggested Changes

- **§5.5 측정 항목에 추가:**
  - profile 전환 시 비용 변화(같은 작업을 audit→poc로 옮길 때 wall-clock·문서량 감소율)
  - trace graph 추천의 precision/recall(Orchestrator가 추천을 수용·수정·기각한 비율)
  - governance 산출물의 **재사용 사례 수**(인수인계, 감리 대응에 실제로 인용된 횟수) — ROI 대리지표
- **§6에 정량 임계 추가.** "Run 생성 시간이 줄고"가 아니라 "Run 생성 wall-clock이 profile별 기준치(예: poc < 5분, solution < 15분) 이하"처럼 측정 가능한 형태로.
- **§7에 시간 축 명시.** "반복되면"이 아니라 "2개 분기 연속 또는 3개 샘플 프로젝트 중 2개에서 관측되면" 같은 trigger.
- **§5에 5.6 "경쟁 흡수 방어" 절 신설.** Core 규칙·Run 계약·Gate 정의를 **adapter-agnostic 사양**으로 외재화하고, Codex/Claude/Cursor 각각의 어댑터에서 동일 산출물이 나오는지를 정합성 지표로 추적.
- **§3의 부적합 조건에 한 줄 추가.** "사용자가 governance 부하를 감당할 수 있는 단일 판단자가 없는 팀" — 다인 팀에서 승인이 분산될 때의 한계를 명시.
- **§5.1에 PoC profile의 구조적 가벼움 메커니즘을 구체화.** 어떤 Gate를 생략/병합하는지, 어떤 traceability를 생략하는지 표로 명시. 그렇지 않으면 §6.5는 달성 불가능한 약속이 된다.
- **§4-3 후속으로 "QA evidence 자동 적재" 검토.** QA worker가 수정하지 않는다는 원칙은 유지하되, FIND/CR/ISSUE 분류 자체는 자동 분류 후보로 측정 대상에 포함.

전반적으로 문서는 draft v0.1로서 충분히 견고하다. v0.2에서 추가할 것은 **새 주장이 아니라 정량 기준**이다.
