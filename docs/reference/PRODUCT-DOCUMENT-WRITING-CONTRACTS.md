# Product Document Writing Contracts

> 상태: 설계용 작성 기준. 설치용 템플릿/필수 검사로 활성화하지 않았다.
> 작성일: 2026-09-09
> 상위 설계: [Product Document Architecture Strategy](PRODUCT-DOCUMENT-ARCHITECTURE-STRATEGY.md)

## 1. 공통 기준

문서의 분량이 아니라 독자가 내려야 하는 판단을 기준으로 작성한다. 아래 항목은 해당 주제를 다룰 때 빠뜨리지 않을 내용이지, 모든 항목마다 새 파일/ID/빈 표를 만들라는 뜻이 아니다.

- 목적/적용 범위, 책임 역할, 현재/후보/과거의 구분, 원본 연결을 짧게 둔다. 기존 metadata/ID를 재사용한다.
- 한 문장에는 가능한 한 한 조건을 적고, 복잡한 조건은 항목으로 분리한다. 설명의 길이를 임의 제한하지 않는다.
- 같은 내용은 한 위치에 쓴다. 다른 문서에서는 ID/제목/원문 절을 연결한다. 단, 독자가 적용할 핵심 경계는 짧게 밝힌다.
- 작업 순서/명령 실행 이력/자기평가를 명세에 덧붙이지 않는다. 결과에는 실제 관측과 미확인을 구별한다.
- 공통 조건은 원본과 적용 범위를 명시한다. 참조된 보안/권한/오류 조건을 읽지 않고 요약만으로 구현하지 않는다.
- 문서에 정보가 없으면 이유/결정 시점을 밝힌다. 비적용을 검토한 경우만 근거와 함께 N/A로 둔다.

## 2. 제품과 요구

| 종류 | 답해야 할 질문 / 적을 내용 | 적지 않을 내용 |
| --- | --- | --- |
| 제품 개요/로드맵 | 누구의 어떤 문제인가? 목표, 사용자, 가치/성공 기준, 이번/제외/후속 범위, 주요 제약과 결정 링크 | 전체 REQ/설계 본문, 날짜별 구현일지, 테스트 로그 |
| 요구사항/기능 명세 | 어떤 상황에서 어떤 동작인가? 기존 ID/제목, 사용자/시나리오, 요구 동작, 업무 규칙/예외, 관측 가능한 AC, 관련 제약/결정 | 내부 클래스/SQL/상세 API 명세, 실제 시험 Pass, 모든 과거 변경의 전문 |

요구사항 목록은 ID/짧은 제목/상세 위치를 기본으로 한다. 상태를 표시하면 원본/추적 상태에서 파생하거나 동일 트랜잭션으로 갱신할 정책이 있어야 한다. 수동 상태 원장을 하나 더 만들지 않는다.

기능 하나가 여러 REQ/AC를 포함할 수 있다. 사용자 관점의 AC와 테스트 입력/기대값을 혼동하지 않는다. AC 원문은 요구사항에, 실행 가능한 케이스는 테스트 정의에 둔다.

## 3. 설계

| 종류 | 적을 내용 | 적지 않을 내용 |
| --- | --- | --- |
| 시스템 아키텍처 | 시스템/외부 경계, 구성요소와 책임, 핵심 실행/배포 흐름, 기술 선택, 품질·위험, 상세 설계/ADR 링크 | 모든 API/컬럼/메서드 목록, 변경 회차별 결론 반복 |
| UX/UI | 사용자 여정, 화면별 목적/탐색, 입력/동작, 로딩·빈 값·성공·오류·권한 상태, 디자인 기준/시안/퍼블리싱 연결, 접근성/반응형 기준 | 스크린샷만으로 동작 정의 대체, DB/API 계약 복사, 디자인 선택 이유의 긴 토론 |
| API/연동 | 대상/권한, 입출력 schema 원본, 상태/오류, 중복/재시도/timeout/호환성 등 적용 계약, 관련 REQ/SEC | 코드에서 생성한 스펙을 승인 계약으로 자동 간주, UI 설명/테스트 로그 |
| 데이터 | 용어·필드 의미, ERD, 타입/키/제약, 관계/수명주기, 분류·보존·이관/복구 기준, schema/migration 원본 | 생성 DDL과 표를 모두 수동 관리, 화면/API별 같은 의미 반복 정의 |
| 보안 | 자산/신뢰 경계, actor/권한, 위협과 보호 조치, 입력/비밀/로그/외부연계 기준, 검증 대상 SEC/잔여 위험 | 범용 OWASP 문구 전체 복사, 아직 검증하지 않은 안전성 보장 |

기능 상태 전이/공개 프로그램 계약은 필요할 때 function/program 상세로 분리한다. 입력·출력·오류·불변조건·트랜잭션 경계와 관련 ID를 기록하며 모든 private helper를 설계 ID로 만들지 않는다. 여러 서비스의 상호작용은 integration 상세에 두고 개별 API/데이터의 원본을 참조한다.

설계 다이어그램에는 목적이 있어야 한다. 구조/시퀀스/상태/ERD/화면 흐름을 해당 질문에 맞게 선택하며 그림만으로 예외/권한 조건을 대체하지 않는다.

## 4. 개발과 검증

| 종류 | 적을 내용 | 적지 않을 내용 |
| --- | --- | --- |
| 개발 가이드 | 지원 도구/버전의 원본, 환경 구성, 코드 구조/관례, 오류·로깅·주석 기준, 로컬 시험/빌드 명령과 성공 조건 | 매 실행 로그, 전역 에이전트 절차, 존재하지 않는 스택의 지침 |
| 테스트/품질 | 정의: 관련 요구/계약, 선행조건, 입력·행동·기대값, 검증 종류. 결과: 대상 소스/환경, 실행/시각, 실제 결과, 증적/결함/미실행 이유 | 정의 문서의 Planned를 실제 실행 없이 Pass로 변경, 같은 시험 결과를 원장마다 재작성 |

테스트 정의와 실행 결과는 별도 수명주기다. 결과는 반복 실행마다 보존하고, 현재 요약은 대상 버전/범위가 맞는 결과를 연결한다. 실행 코드가 있는 경우 케이스와 테스트 위치를 연결하며 로그 전문은 로그 파일에 둔다.

실행 묶음에는 소스뿐 아니라 당시 테스트 정의의 Git 기준 또는 보존 스냅샷을 한 번 연결한다. 수동 시험도 동일하다. 정의가 바뀐 뒤 같은 테스트 ID의 과거 Pass를 새 기대값을 검증한 결과로 해석하지 않는다. 기대값 본문을 결과에 다시 복사할 필요는 없다.

## 5. 운영과 결정과 사용자 안내

| 종류 | 적을 내용 | 적지 않을 내용 |
| --- | --- | --- |
| 배포/운영 | 대상 환경/설정, 배포·migration·롤백·복구 절차, 준비/성공/중단 조건, 모니터링/알림/백업, 책임/권한. 릴리즈별 범위/승인/known issue는 릴리즈 기록 | secret 값, 실행하지 않은 배포 성공, 구현 self-check만으로 운영 인수 완료 |
| 변경/의사결정 | CR: 변경 이유/범위/영향/승인/이관 책임. ADR: 문제/제약/선택/대안/결과. 대체 시 연결 | 현재 요구/설계의 영구 복사본, 모든 작은 수정의 ADR, 대화 전문 |
| 사용자 안내 | 실제 제공 기능의 시작/사용 절차, 입력·예상 결과·문제 해결, 설정 참조와 개념 설명 | 내부 Gate/Run 절차, 제공하지 않는 후보 기능을 현재 기능으로 설명 |

긴 ADR_LOG는 목록과 건별 결정으로 분리할 수 있다. 이것이 모든 ADR을 새 형식으로 재작성하라는 뜻은 아니다. 불변의 결정/실행 기록과 현행 운영 절차를 혼합하지 않는다.

미해결 시험/결함은 기존 FIND/ISSUE/CR 중 관리 원본을 하나 정해 적용 조건, 담당, 시험/결과, 종료 근거를 유지한다. 릴리즈 범위 축소만으로 종료하거나 일반 개선 백로그로 격하하지 않는다.

## 6. 간단한 모양 예시

아래는 요구사항 상세의 작성 모양을 설명하는 합성 예시이며 실제 프로젝트 요구사항이 아니다. 런타임 parser에 등록된 새 템플릿도 아니다.

```markdown
# 알림 설정

상태: 검토 후보 / 책임: 요구 담당 / 범위: 로그인 사용자 본인

## REQ-901 알림 수신 설정

사용자는 본인의 알림 수신 여부를 변경할 수 있다.

조건:
- 다른 사용자의 설정을 조회하거나 바꾸지 않는다.
- 저장에 실패하면 이전 설정을 유지하고 실패를 알린다.

인수조건:
- AC-901: 저장 성공 후 다시 열면 선택한 값이 보인다.
- AC-902: 저장 실패 시 이전 값이 유지되고 재시도할 수 있다.

연결: 적용 권한 정책, 화면 상세, 관련 결정의 원본 절.
```

화면 디자인, API schema, DB 컬럼, 실패 시험의 입력값과 실제 결과는 이 문서에 이어 붙이지 않는다. 각각 해당 설계/시험/실행 기록에 연결한다.

## 7. 검토 종료 기준

1. 문서만 읽고 대상 판단을 할 수 있는가? 참조가 필요하면 위치/적용 범위가 명확한가?
2. 조건·예외·권한과 미해결 책임을 줄인 분량 속에 숨기지 않았는가?
3. 같은 계약을 두 곳에서 수정하게 만들지 않았는가?
4. 후보/현재/이력과 승인/구현/시험 상태를 혼동하지 않았는가?
5. 원문/표/스키마/로그의 전문을 반복하거나 작업 서술을 명세에 넣지 않았는가?

파일 수나 경고 0개가 완료 기준은 아니다. 검사 자동화가 이 기준을 전부 의미적으로 증명한다고 주장하지 않는다.
