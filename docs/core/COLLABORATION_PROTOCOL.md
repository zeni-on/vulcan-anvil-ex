# Role-Based Collaboration

> 역할별 지속 작업과 일시적인 worker의 공통 규칙이다. 실행 도구를 새로 만들거나 Gate/Profile/Run 스키마를 바꾸지 않는다.

## 1. 적용과 역할

사용자가 역할별 협업을 선택한 경우에 적용한다. 작업창(thread)은 대화와 실행 공간이고, persona는 책임이며, Run 또는 허용된 결과 요약은 개별 업무 단위다. 하나의 역할 작업창에서 여러 업무를 순차 수행할 수 있다. 작업창 이름이나 같은 프로젝트 소속만으로 권한, 문맥 공유, 파일 격리, 자동 실행이 생기지는 않는다.

| 역할 예시 | 기존 persona | 담당 결과 |
| --- | --- | --- |
| 총괄 | Orchestrator | 사용자 요청/승인, 배정, 통합, 공통 상태와 다음 판단 |
| 설계 | requirements / design | 요구사항 및 API/DB/보안/아키텍처 계약과 미확정 사항 |
| 경험설계 | design | 사용자 흐름, 화면 상태, UI 디자인/퍼블리싱 계약 |
| 개발 | build | 승인 범위의 코드와 담당 테스트, 계약/추적 갱신 후보 |
| 품질검증 | test-design / evidence / review | 테스트 계획, 실행 증적, 결함/환경 차단/증적 부족 구분 |

위 역할 수와 이름은 예시이지 필수 목록이 아니다. 담당자는 배정 시점의 persona와 승인된 Gate 범위만 수행한다. 역할별로 Ex 전체 시작 루틴이나 문서 원장 정리를 반복하지 않는다. 공통 Guardrails와 해당 작업의 보안/검증 계약은 유지한다.

## 2. 문서와 상태 소유권

- 총괄만 승인 근거를 취합하고 Gate/Wave/session 상태, 최종 추적표 및 통합 판정을 갱신한다. 사용자 승인이 필요한 지점은 그대로 남으며 담당자의 완료나 동의로 대신하지 않는다.
- 담당 문서/코드/테스트/증적의 실제 작성자는 배정한 `scope.writable`로 정한다. 역할 이름만으로 전체 설계 폴더나 원장 수정 권한을 주지 않는다.
- Product의 6종 원장은 역할별로 복제하지 않는다. 설계와 경험설계가 같은 문서를 다루면 한 명이 작성하고 다른 담당자는 변경 후보를 반환하거나, 쓰기 순서를 정한다. 총괄의 최종 정리는 담당자의 쓰기가 끝난 뒤 수행한다.
- 총괄의 최종 QA 결과서/추적표 정리와 QA 담당자의 개별 실행 증적 작성을 구분한다. QA 실패를 본 담당자가 임의로 소스나 승인된 설계를 고치지 않고, 기존 `qa-fix-loop`/변경관리 절차로 반환한다.
- 같은 Local 경로의 작업은 파일과 Git index/checkout을 공유한다. 담당자들이 동시에 branch switch, commit, merge 또는 같은 파일 쓰기를 수행하지 않는다. 역할별 worktree를 사용해도 공통 원장의 통합 책임은 총괄에게 있다.
- 작업공간 복제본의 `session.json`은 배정 당시 입력이다. 각 복제본에서 별도의 Gate를 진행하지 않는다. 총괄은 새 업무 배정 전 현재 기준과 차이를 확인한다.

## 3. 짧은 작업 전달

총괄은 기존 Run/Orchestrator Plan 또는 Profile에서 허용한 작업 요약에 다음 정보를 연결한다. 이미 Run에 있는 값은 본문을 복제하지 않고 경로/구간을 가리킨다. 새 필수 문서나 이중 작업 목록은 만들지 않는다.

| 정보 | 전달 내용 |
| --- | --- |
| 대상 | 실행 도구가 반환한 식별자/경로와 역할, 이번 Run 또는 업무 식별 |
| 기준 | 현재 Gate/Profile, 승인 범위, 실제 작업공간, branch/commit 또는 관찰 가능한 dirty 기준 |
| 입력 | 관련 ID, 원본 문서 구간과 공통 제약, 필요한 변경점 |
| 경계 | 수정 허용 파일, 제외 범위, 의존 작업과 쓰기 순서 |
| 완료 | 수행할 검증 명령/cwd와 결과 위치, 총괄에게 반환할 항목 |

기준과 식별자를 알 수 없으면 추정하지 말고 확인한다. 현재 계약 구간과 검증 소스 식별은 [Current Context And Evidence](CURRENT_CONTEXT_AND_EVIDENCE.md)를 따른다. 잘린 구간/미분류/서로 다른 계약은 승인된 사실로 간주하지 않는다. 공통 보안 조건을 읽기 범위에서 빠뜨리지 않는다.

Run을 사용하는 native worker는 위임 전 `run-preflight` 또는 이를 포함한 `execute --dry-run` 통과를 확인한다. 계약/범위/Run/프로젝트 상태가 바뀌면 재검사한다. Product는 [PRODUCT_PROFILE_BASELINE.md](PRODUCT_PROFILE_BASELINE.md) 7절에 따라 기존 작업/이슈 요약으로 전달할 수 있다. PoC의 기존 Run 생략 기준도 유지한다. 역할 작업창을 사용한다는 이유로 Run을 추가하지 않는다.

## 4. 전달, 회수, 다음 행동

1. 총괄은 대상 역할과 실제 실행 위치를 확인하고 한 번에 경계가 분명한 업무를 전달한다. 이미 수행 중인 업무를 모르면서 중복 배정하지 않는다.
2. 담당자는 현재 배정이 이전 대화와 다르면 최신 승인 계약을 기준으로 차이를 확인한다. 불명확한 계약, scope 밖 수정, 의존 작업 변경은 총괄에게 반환한다. 다른 역할에 다시 일을 넘기려면 총괄의 명시적 배정이 필요하다.
3. 총괄은 완료 알림이나 긴 대기를 사용하고, 범위 변경/차단 해소가 있을 때만 추가 지시한다. 역할 작업창을 만들었다고 상시 실행하거나 반복적으로 상태/문서를 읽히지 않는다.
4. 담당자는 변경 파일, 실행한 명령/cwd/결과와 증적 경로, 남은 질문/FIND/CR/ISSUE 후보를 반환한다. 테스트를 실행하지 않았으면 이유와 `Not Run` 또는 `environment_blocked`를 구분한다.
5. 총괄은 실제 diff/scope/소스 기준과 증적을 확인하고 필요한 재검증 후 통합한다. 기존 작업 결과에 위임 대상/범위/검증을 기록하고, Run이 있으면 [Run Output Contract](RUN_OUTPUT_CONTRACT.md)의 `delegation_records`를 사용한다. 역할 작업창 하나에 대한 영구 완료가 아니라 개별 업무의 결과를 기록한다.
6. 사용자 질문과 승인 요청은 총괄이 모아 전달한다. 도구가 사용자 보안 승인을 직접 요구하면 우회하지 않는다. 도구/대상 연결이 없거나 결과 회수가 안 되면 그 한계를 보고하고, 완료나 다음 Gate로 추정하지 않는다.

실행 위치나 기준선이 달라졌거나 통합 중 코드가 바뀌었다면 과거 검증이 그대로 유효하다고 간주하지 않는다. Product의 재실행 범위는 [Product Profile Baseline](PRODUCT_PROFILE_BASELINE.md) 7절에 따라 정한다. 담당자 self-check를 무조건 반복하거나 문서 정리만으로 제품 테스트를 재실행하지 않는다.

## 5. 병렬 작업과 독립 검수

- 승인된 같은 단계 안의 독립 조사/설계 후보/증적 분석은 충돌 없이 병렬 수행할 수 있다. 역할을 나눴다는 이유로 다음 Gate나 의존 계약이 확정되지 않은 구현을 먼저 진행하지 않는다.
- Wave를 선택한 경우 [Agent Run Protocol](AGENT_RUN_PROTOCOL.md)의 단일 active Build Wave 규칙을 유지한다. 여러 개발 작업창을 만들었다고 다중 Wave나 한 Wave의 여러 구현 runner를 자동 허용하지 않는다.
- QA는 지정된 통합 소스와 QA workspace를 확인한다. 테스트 도중 다른 담당자가 해당 소스/DB/서버/포트를 변경하지 않도록 검증 구간을 조율한다. 역할마다 QA 환경을 새로 만들지는 않는다.
- 오래 유지한 품질검증 담당은 프로젝트 맥락을 가진 QA 담당이다. 중요한 독립 리뷰에는 [새 문맥의 native review](AGENT_RUN_PROTOCOL.md#54-새-문맥의-native-review)를 적용하고, 구현에 참여한 작업이나 그 대화를 복제한 작업을 독립 reviewer로 간주하지 않는다.
- 모든 역할을 매 업무에 호출하지 않는다. 필요한 관점/산출물만 요청하고, 모든 대화/로그 전달이나 동일 테스트의 중복 실행으로 조율 비용을 늘리지 않는다.

## 6. 런타임 연결과 검증 범위

Core는 실행 매체와 무관한 계약이다. Codex 작업창 연결은 [Codex Persona Delegation](../adapters/codex-gpt/PERSONA_DELEGATION.md), 다른 런타임은 해당 adapter를 따른다. 외부 CLI와 `agent-run`/`run-exec`는 계속 선택 사항이다.

이 문서는 정책이며 자동 dispatcher, 스케줄러, 작업창 registry 또는 파일 잠금을 구현하지 않는다. 배정/회수 도구 제공 여부를 실제 환경에서 확인한다. 정책 파일 설치 검증과 실제 역할 작업창 간 통신 검증을 구분한다. 작은 승인된 업무로 입력 전달, 결과 회수, 단일 작성자, 차단 보고를 먼저 확인한다.
