# Vulcan-Anvil Ex v0.5.0

- 기록일: 2026-09-13
- 범위: 공개 버전 `v0.4.9` 이후 병합된 변경
- 성격: 신규 Product 기본 프로세스가 바뀌는 마이너 릴리즈. 실험 단계이며 업무 정확성·보안·감리 적합성을 자동 인증하지 않음

## 무엇이 좋아졌나

| 이전에 불편했던 점 | 이번 변경 | 사용자에게 달라지는 점 |
| --- | --- | --- |
| 코드는 요구대로 만들었지만 실제 업무 흐름과 어긋남 | 문제·경계·액터·규칙·예시에서 REQ/AC와 시험으로 연결 | 상세 구현 전에 중요한 업무 판단을 총괄과 확인할 수 있음 |
| 기능이 늘면 원장 6종에 설명과 이력이 계속 쌓임 | 6종은 진입점으로 두고 기능별 원본과 현재/후보/과거 내용을 구분 | 필요한 계약을 찾아 수정하고, 전체 문서를 복제하지 않음 |
| 작은 수정마다 Run/Wave와 같은 시험을 반복 | Product Run/Wave 선택화, 담당 입력·검증 범위 축소 | 문서 정리와 경고 제거에 쓰는 불필요한 작업을 줄임 |
| Gate를 차례대로 다시 밟는 운영 부담 | 신규 Product의 기획·설계 ↔ 구현 ↔ 인수 검증 | 새 기능을 같은 제품 안에서 반복하고 과거 인수·이력을 보존 |
| worker 완료와 실제 검증·승인이 섞임 | 실행 결과 회수와 인수 결정·릴리즈 권한 분리 | 무엇을 검증했고 무엇이 아직 승인되지 않았는지 구분 |
| Ex 자체만 검사하고 제품 CI 연결은 불명확 | 실제 요청 보드와 제품별 GitHub Actions 예시 | 기존 제품 테스트를 CI에서 반복하고 실패·미실행을 확인하는 참고 경로 확보 |

시간·비용 절감률을 입증한 벤치마크는 아니다. 줄인 절차의 효과와 모델별 성능은 실제 업무 범위, 입력량, 재시도와 총괄의 보정량에 따라 달라진다.

## 신규 Product 시작과 반복

```powershell
python vulcan.py init ../my-product "My Product" --profile product
```

`product-iterative-v1`의 `planning`으로 시작한다. 총괄이 실제 목표·포함/제외 범위·계약·시험 계획을 합의하고 기존 상태 요청의 미리보기/적용을 맡는다. 사용자가 JSON을 손으로 작성할 필요는 없다. 최초 `status --check`가 빈 범위의 구현 진입을 차단하는 것은 정상이며, 합의하지 않은 요구나 Pass를 만들어 채우지 않는다.

- `planning`: 업무·요구·설계·시험 계획을 함께 다듬는다. 문서 절마다 별도 승인을 늘리지 않는다.
- `impl`: 승인된 범위를 구현하고 필요한 검증을 수행한다. Run과 외부 CLI runner는 필요할 때 선택한다.
- `acceptance`: 현재 범위의 실제 시험 결과를 회수하고 인수 여부를 별도로 결정한다.
- `completed`: 이번 범위가 인수됐다는 결과다. 제품 전체 완료나 배포 완료가 아니며 새 범위를 열어 반복할 수 있다.

준비 검사 성공, 구현 허가, 실제 테스트 성공, 인수 결정과 릴리즈 권한은 서로 대신하지 않는다. 실패·누락·환경 차단과 오래된 승인/결과 재사용을 검사한다. [첫 사용 절차](../core/ORCHESTRATOR_CLI_GUIDE.md#41-개발용-product-반복-프로세스), [업무·문서 작성](../core/PRODUCT_DOCUMENT_WRITING.md)을 참고한다.

## 문서·에이전트·Dashboard

- 요구/AC, API, DB·ERD, UI 디자인·계약, 보안, 개발·빌드·배포 기준, 시험 계획과 실행 결과의 상세 양식을 필요한 곳에서 사용한다. 모든 문서를 의무적으로 만들지 않는다.
- `trace-context`의 절 조회와 상대 링크 추적, 분리 원본 검사로 현재 계약을 찾는다. 잘림·미분류·누락을 숨기지 않으며 조회 결과 자체를 승인으로 보지 않는다.
- 역할별 지속 작업의 소유권·전달·회수를 정리했다. Product worker가 총괄의 문서 정리와 상태 갱신까지 반복 수행하지 않는다.
- Codex native는 사용자 모델 설정 상속과 작업별 effort를 사용한다. 중요 검토는 필요에 따라 새 문맥으로 수행하며 외부 모델은 선택 사항이다. 앱/API 기능이나 모델 설정이 문서만으로 자동 적용된다고 주장하지 않는다.
- Dashboard는 Product의 세 구간·현재 작업 범위를 읽기 전용으로 표시한다. 문서를 분야별로 분류하고 로컬 접근·경로·출처 보호와 의존성 검사를 보강했다.
- `doctor`, release, status 내부 로직을 `vulcan_core`로 나눴다. 기존 CLI 호환을 유지하며 별도 앱 서버나 자동 dispatcher는 추가하지 않았다.

## 업그레이드

먼저 Ex 저장소에서 최신 `main`을 받는다.

```powershell
git pull --ff-only
```

대상 프로젝트 폴더에서 실행한다.

```powershell
python vulcan.py upgrade
python vulcan.py version
python vulcan.py status
```

- 표식 없는 기존 Product, Audit, PoC는 기존 Gate 흐름을 유지한다. PMTool 같은 기존 프로젝트도 자동 이행하지 않는다. 새 흐름을 만들려고 `process_model`을 직접 추가하거나 `init`을 덮어 실행하지 않는다.
- 이미 반복 프로세스를 사용하는 Product는 현재 범위·결정·이력을 보존한다. upgrade는 최신 세션을 잠금 안에서 읽고 프레임워크 source/version만 갱신한다. 작성한 산출물·코드·기존 실행 기록을 자동 이동하거나 재작성하지 않는다.
- 실행 중인 worker와 상태 변경을 정리한 뒤 upgrade한다. 프레임워크 파일 복사 전체가 원자적인 것은 아니므로 IO 실패 시 현재 상태와 원본을 확인한다.
- Dashboard는 Ex 저장소의 `dashboard/`에서 `npm ci` 후 서버를 재시작한다. 프로젝트 upgrade만으로 실행 중인 Dashboard가 갱신되지는 않는다.

[업그레이드 안내](../UPGRADE_AND_DASHBOARD.md)에 기존 Gate 프로젝트와 새 Product의 경계를 구분했다.

## 검증 근거와 한계

릴리즈 준비 이전의 병합된 기능 검증 근거다. 최종 배포 커밋의 CI 상태는 해당 릴리즈 PR의 Checks에서 확인한다.

- [신규 초기화·호환 검증](../reference/PRODUCT-NEW-PROJECT-VERIFICATION.md): Python 354건(로컬 351 Pass/3 Windows symlink skip), Audit init 12단계, legacy fixture 84단계, Dashboard Jest 310건 및 Product 화면 검증. PR #49의 Windows/Linux·Dashboard·제품 CI 완료.
- [실제 요청 보드](../../examples/product-request-board/docs/verification.md), [제품 CI](../../examples/product-request-board/docs/ci-verification.md), [동일 제품의 기능 확장](../../examples/product-request-board/docs/iteration-verification.md): UI/API/SQLite의 반려·재제출·이력 보존과 후속 확장을 실행하고, 고의 결함 및 누락을 감지하는 회귀를 확인했다.
- [마지막 지침 정리 PR #50](https://github.com/zeni-on/vulcan-anvil-ex/pull/50): Product 정책 시험 12건과 CI 확인. 자연어 지침 전체의 의미적 정합성을 자동 증명하는 것은 아니다.
- Codex/Agy/Claude primary 설치·문서 라우팅과 각 모델 런타임의 실제 수행 검증은 다르다. 모든 외부 런타임의 동작·속도를 검증했다고 확대하지 않는다.
- 저장 상태와 테스트 기록은 업무 합의, 실제 운영 권한, 보안 적합성, 시험 충분성을 대신하지 않는다. Dashboard가 승인 신원을 인증하거나 자동 배포하지 않는다.
- 누적 session의 기존 8MB 제한, 기존 프로젝트의 수동 이행 판단, `release-pr --dry-run` 후보 이후 별도 승인된 발행 경계는 유지한다.

미병합 Spec-to-Scaffold PR #15, 기존 프로젝트 자동 전환, Audit 프로세스 재설계, 자동 작업 배정·배포와 일괄 모델 변경은 포함하지 않는다. 합의한 여섯 고도화 항목은 완료했으며 이후에는 실제 사용에서 확인한 문제를 중심으로 보완한다.
